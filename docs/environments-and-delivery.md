Rosetta is a web application with accounts, shipped as one container image that runs next to PostgreSQL, locally
with Docker Compose and hosted on a container host (DEC-59, DEC-61, DEC-65; ADR-014, ADR-016). This document is the canonical home of the package and tool baseline (section 7).

## 5. Source control and branching

- Repository: public GitHub `blacklight0101/Rosetta`, default branch `main` (DEC-06).
- Flow (DEC-35): issue per card -> branch `task/<card-id>-<slug>` or `docs/<topic>` -> pull request from the template
  -> CI green -> verifier verdict posted -> squash merge by the orchestrator under the merge rules of the orchestration protocol section 3.1, or by the owner for `needs-owner` pull requests (DEC-96) -> branch deleted.
- `main` is protected by a repository ruleset: changes only through pull requests, squash merge only, linear history,
  no force-push, no deletion, review threads resolved before merge, no required approving review (the orchestrator
  and the owner use the same GitHub account, which cannot approve its own pull request; DEC-96). The owner adds the CI
  jobs as required status checks to the ruleset once P1-02 has merged the workflow; from then on no pull request can
  be merged with a red check.
- **Required checks.** The owner adds these job names to the `main` ruleset as required status checks:
  `verify (ubuntu-latest)`, `verify (windows-latest)`, `e2e`, `audit`, `gitleaks`, `dependency-review` (all in
  `.github/workflows/ci.yml`), `pr-title` (`.github/workflows/pr-title.yml`) and `codeql`
  (`.github/workflows/codeql.yml`). Jobs that later cards add to the table of
  section 6 (image build and scan, Compose smoke test) join this list in the card that adds them. The `audit` job
  runs `scripts/audit-check.mjs`, which reads `audit-exceptions.json`: a JSON array of
  `{ "id": "GHSA-xxxx-xxxx-xxxx", "reason": "...", "expires": "YYYY-MM-DD" }`, empty by default; an expired entry stops
  applying and the advisory fails the job again.
- Commits follow Conventional Commits, checked by commitlint ([conventions](conventions.md) section 9).
- Git hooks (lefthook): `pre-commit` formats and lints staged files; `commit-msg` runs commitlint; `pre-push` runs
  `typecheck` and the unit tests. Hooks help; CI is the gate. Humans install them with `npm run hooks:install`
  (a plain `npm ci` also does, through lefthook's postinstall). Agents install with `npm ci --ignore-scripts`,
  because worktrees share one `.git/hooks` folder; `LEFTHOOK=0` does not stop the postinstall, `CI=true` does
  (see `lefthook.yml`).

`npm run verify` runs the first six checks locally in the same order; builders and the verifier run it on every card.

**Windows runs the tests only** (added 2026-10-13). The `verify (ubuntu-latest)` job runs `npm run verify`, every
gate above; the `verify (windows-latest)` job runs only `npm run test:ci`. Type check, lint, format, architecture and
dead-code checks give the same answer on both operating systems, so running them twice bought nothing; the tests are
what catches path, line-ending and process differences. Both job names stay the same, because both are required
checks.

**No caches beyond `setup-node`'s npm cache** (measured 2026-10-13 on pull request #304). The extra caches tried
did not pay for themselves, so none is used:

- _Playwright browsers_ (`~/.cache/ms-playwright` per `@playwright/test` version): on a hit a job still has to run
  `npx playwright install-deps chromium`, because the runner keeps no system packages. A cold
  `install --with-deps` took 19 to 23 s; a cache restore plus `install-deps` took 15 to 26 s.
- _Prettier_ (`--cache --cache-strategy content`): the format check fell from about 7 s to about 3 s, and the
  cache restore and save cost about the same.
- _ESLint_ (`--cache`): not used even though it is fast, because it is unsound here. ESLint's cache keys each file
  on its own content, but the type-aware rules of the configuration also read the files it imports: a change in
  one file can create an error in another that the cache then reports as clean. Lint always runs in full.

**Documentation-only pull requests** (added 2026-10-13). A first job, `changes`, compares the pull request with its
base using plain git (`git diff --name-only --no-renames base...head`, full history, no third-party action;
`--no-renames` lists both paths of a moved file, so moving code or a prompt into `docs/` still counts as code) and
sets `code=false` only when every changed file is documentation: anything under `docs/`, or a `*.md` file at the
repository root. Markdown anywhere else (`src/`, `tests/`, `prompts/`, `templates/`, `scripts/` and so on) counts as
code, because some of it ships in the image or is read at run time. A push to `main` always counts as code. The jobs
`verify`, `e2e-shard`, `image` and `compose-smoke` always run and need `changes`. Their heavy steps run unless `code`
is exactly `false` (`needs.changes.outputs.code != 'false'`), so a missing or unexpected value fails closed. The
steps are skipped by a step-level `if:`, never a job-level one, because a skipped matrix job
reports an unexpanded name and the required checks `verify (ubuntu-latest)` and `verify (windows-latest)` would
never arrive. The `e2e` check stays green, since shards whose steps were skipped still succeed. For a
documentation-only change the Linux `verify` job still runs `npm run format:check` and the tests that read the
documents: `tests/integration/docs/`, the workflow tests, `release-schema.test.ts` (against `data-model.md`),
`status-badge.test.tsx` (against `architecture.md`) and `tokens.test.ts` (against `docs/design/tokens.css`);
`workflow-docs-only.test.ts` fails when a test that reads `docs/` is missing from that list. `audit`, `gitleaks`,
`dependency-review` and `pr-title` run as before. The `changes` job is not a required check: if it fails, the
jobs that need it do not run and the required checks stay missing, so the pull request cannot merge.

**Edits of a pull request** (P1-146). `ci.yml` runs on `opened`, `synchronize` and `reopened` only. An edit of the
title or the body starts `pr-title.yml` alone, which runs `pr-title` and nothing else. The alternative, a job skipped
by an `if:` on `edited`, was rejected: a skipped check reports as passed, so it would replace a failed result of the
same commit and let a red pull request merge after an edit of its body, and the edit would also cancel a running
run (the `ci-<ref>` concurrency group). An edit does not create a check run for `verify`, `e2e` or the other
required checks, so the results of the run on the head commit stay the ones GitHub reads. `codeql.yml` does not
list `edited` either, so GitHub's default types (`opened`, `synchronize`, `reopened`) apply to it.

Workflow hardening: `timeout-minutes` on every job (15 for checks); `actions/setup-node` with `cache: npm`; `npm audit`
exceptions only in `audit-exceptions.json`, each with a reason and an expiry date; top-level `permissions: contents: read`; third-party actions pinned to a full commit SHA with the
version in a comment; no `pull_request_target`; no secrets in CI (tests never call providers). Dependabot updates npm
packages and GitHub Actions weekly, grouped by minor and patch, with a 14-day cooldown so it proposes only
versions that are two weeks old (DEC-125).

## 8. Versioning and releases

- Semantic Versioning in 0.x (DEC-29); `v0.1.0` is the 2026-10-26 milestone.
- A release is a pull request that bumps `package.json`, adds a section to `docs/releases.md`, merges, then a tag
  `vX.Y.Z` and a GitHub release with the same notes; the owner creates the tag.
- Cadence: one release per phase exit; patch releases as needed.
- Build once: the release job builds the image once, pushes it to GHCR as `X.Y.Z` and `sha-<short>`, and attaches a
  CycloneDX SBOM (`npm sbom --sbom-format cyclonedx`) to the GitHub release (DEC-57). Every deployment uses that
  exact tag. Before the first release (v0.1.0), the hosted deployment runs the `sha-<short>` image that CI built from
  `main` (DEC-104).
- The release job is `.github/workflows/release.yml` (P1-55): it runs only on a pushed `v*` tag or by hand on `main`
  (never on a pull request or a push to `main`); jobs `image` (tag checks, build, Trivy, push with the job token),
  `sbom` (tags only) and `deploy`, which stays skipped until the repository variable `ROSETTA_DEPLOY_ENABLED` is
  `true` and runs in the GitHub environment `production` (its secrets and variables: `docs/runbooks/deploy.md`). The
  deploy job is the only place a workflow reads secrets.
- The `Dockerfile` has a `test` stage with the fake provider and fake GitHub, used only by `compose.ci.yaml`; the
  runtime image ships no tests and no scripts; the compiled fakes inside `dist` are reachable only with `ROSETTA_TEST=1`, and `kind: fake` is refused without it (DEC-112).
- After the GitHub Pages deploy, a smoke-test step fetches the published report's index and fails the job (`exit 1`)
  if it is missing or does not contain the run id.

## 9. Database deployment

PostgreSQL 17 (ADR-016). Locally the `db` service of `compose.yaml` with the `pgdata` volume; hosted a managed
PostgreSQL. A one-off migrate step of the same image (`node dist/presentation/migrate.js`, the `migrate` service of
`compose.yaml`; a one-off job before the deploy when hosted) applies pending migrations with `DATABASE_MIGRATOR_URL`
and ends; the app starts only after it succeeded, with `DATABASE_URL` only, and refuses a pending (RST-2405), changed
or unknown migration (RF-1302, DEC-140). A migration that fails ends the step with an error, leaves the previous
schema, and the app is not started. The roles of data-model.md section 6 are created locally by the Compose init
script `db/init/roles.sh` (passwords from `.env`) and hosted in the host's console (runbook); migrations only grant
(DEC-112).

## 10. Deployment procedure

1. All cards of the phase merged, CI green on `main` (including the image scan, the Compose smoke test and the ZAP baseline).
2. Local: `docker compose pull` (or `build`), `docker compose up -d`, sign in, run the demo `scan` and `understand`
   (RF-801, RF-1301).
3. Release pull request, merge, tag; the release job pushes the image to GHCR.
4. Hosted: run the OWASP ZAP baseline scan against the local Compose stack (threat model section 5); back up the
   database (host snapshot), run the migrate step of the new image as a one-off job that holds `DATABASE_MIGRATOR_URL`
   as its only secret (DEC-140), set the new image tag on the host, wait for `/healthz`, run the smoke test (landing,
   sign-in with the teacher account, a cheap scan, which needs no provider) (RF-1304).
5. Regenerate the sample report into `site/` in a pull request; merge; GitHub Pages publishes it (RF-800).
6. Record the deployed tag and date in `docs/runbooks/deploy.md` and `handoff.md`.

## 11. Rollback

Hosted: set the previous image tag. Migrations are additive within release 1, so the previous image runs on the newer
schema; a migration that is not additive is announced in the release notes with its restore point (the backup of
step 4). Local: `docker compose up -d` with the previous tag. The sample report is restored by reverting the pull
request that changed `site/`.

## 12. Backup and restore

- Code and documents: the repository on GitHub.
- Database: the host's daily backups kept 7 days, or a scheduled `pg_dump` to the disk when the host has none; one
  snapshot before every deployment (RF-1306).
- Data folder: weekly copy of `users/` (snapshots can be downloaded again).
- `ROSETTA_SECRET_KEY` is kept by the owner outside the host as well; without it the stored user keys cannot be
  decrypted.
- One restore drill into the local Compose stack is recorded in `docs/runbooks/deploy.md`.

## 13. Observability

- Every run writes its manifest, egress log, cost report, run events and provider call log (RF-003, RF-142, RF-426,
  RF-1006, RF-408); every call is a row in the cost ledger (RF-428); account events are in the audit table (RF-1109).
- Every provider interaction (Ollama or cloud) is one record with timing, tokens, cost, retries and status, shown live
  in the web UI (RF-408, RF-1011).
- Rosetta's own log: structured JSON lines on standard output at `ROSETTA_LOG_LEVEL` (collected by Docker or the
  host) and in `<data>/logs/`, daily files kept 14 days, `debug` and above (RF-009).
- `/healthz` for the host's health check (RF-1303); the administrator's page shows the server month against its cap
  (RF-1106).
- Logs and records pass through the secret masking and never contain secrets or API keys (RNF-003).
- No telemetry: Rosetta sends nothing anywhere except to the providers the user configures.
- Latency is reported as P50 and P95, never as an average alone (RF-1011); provider calls carry trace and span ids
  mapped to the OpenTelemetry GenAI conventions (data-model.md section 3.10).

## 15. Naming of environments in code and configuration

`ROSETTA_TEST=1`, which makes any real provider adapter refuse to call the network (ADR-008).
