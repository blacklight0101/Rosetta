# Baseline of every prompt on Haiku, Sonnet and Opus (P10-04)

Status 2026-11-13: **the baseline has run.** Every committed lab case set except the two hand-written samples was run on the current version of its prompt with `--split tune`. Haiku 5.5 ran all its tune cases; Sonnet 5.5 and Opus 5.5 ran a deterministic sample (`--sample`, RF-1409). Opus 5.5 judged. The card spent **$3.4573 of its $6 slice**; the shared ledger stands at **$5.9987** (stop line $40, cap $50), so $34.0 remain under the stop line. Per-case results are in `lab-out/<id>/results.json` (git-ignored); the run ids are in the appendix.

Read this first, because it changes how much the numbers can carry:

1. **Sonnet and Opus rest on 1 to 4 cases per set (61 and 39 cases in all), so their figures are indicative only.** Haiku has all 125 tune cases.
2. **The judge ran on a sample, not on every run.** Haiku: one extra judged run per set (`--sample 1`, three for each shared set), 31 judged cases. Sonnet and Opus: judged only on the two shared sets (5 and 4 cases). The verifier sample was judged on all three models. Nowhere else did Sonnet or Opus get a judge, to stay inside $6. The judge columns for Haiku come from the judged sample run, not from the full run next to them.
3. **The judge cannot score a reader first turn or `shared/masked-value`.** The lab replays one turn; a model that answers with a tool call produces an empty answer text, which the judge then scores 1 (a veto). Those 1.0 scores are artefacts of the replay, not findings about the prompts, and are marked `artefact` in the table. The remedy is in the order below (P10-05 starts with it).
4. **A tune case that ends "reads more" counts as unusable.** A replay has no tool results to give back, so a model that asks to read another file (`ReadsMore`) is counted unusable and disagrees with a `Valid` label. That is a property of the replay as much as of the prompt, and stronger models do it more.
5. **`verifier/claim` has only the 4-case hand-labelled sample** (`verifier-claim-sample`, 100 percent agreement on all three models). It has no tune/held-back split, was run whole, and is too small to rank on. P10-06 has to build a real verifier set first (from the hand-labelled claims of `eval/calibration/`).
6. **Trust in the judge** (`judge-sample.md`): the verifier and shared families agreed with the hand scores best; cards and planner are flagged **advisory** (cards fidelity and format-validity, planner actionability and consistency fell short of the proposed default). Reader and summariser agreed in the middle.

## The worst cases

One line each; quotes are a few words of model output at most. The ids are `lab/cases/` case ids.

- **`planner/data-model`, `eshop-20261023-152751-plan-planner-data-model`**: unusable on all three models. Each answers with an empty `tables` list and a `dropped` list, and the parser refuses it. Haiku's judged run scored the same answer 4.8, so it is likely a case/parser mismatch (a valid "nothing to derive" answer), not a model weakness. The same case appears in every model's unusable count for this set.
- **`shared/masked-value`, `shipping-password-constant`, `inventory-bearer-script`, `payroll-xml-password`, `deploy-script-flag`**: Haiku asked to read more instead of giving the final answer on 4 of 5 cases (label `Valid`). Opus 2 of 2 and Sonnet 1 of 2 did the same (Sonnet once flagged "not reported at all" for `inventory-bearer-script`).
- **`shared/text-tool-protocol`, `clinic-first-turn` (Haiku)**: a bare JSON object with `"name": "read_file"` instead of the fenced `tool_call` block (outcome `Answered`, label `ReadsFiles`). **`garage-first-turn` (Sonnet)**: an `<invoke>` XML block, a different protocol, and the judge saw invented file contents (grounding 1). **`library-after-reads`, `school-after-reads`, `garage-after-reads`**: Haiku read more after reading a few lines instead of answering (label `Valid`); `garage-after-reads` also reads more on Sonnet and Opus.

## Ranking: cost share in a real run times failure

**How the cost share was estimated.** `docs/evaluation/` holds no per-run call counts, so the share is an estimate with three inputs. (a) Tokens: the measured cost per call of each prompt on Haiku in this baseline (prices scale the same on the three models, so the share does not depend on the model). (b) Calls per run: the call ids of the committed sets run up to 197 in an `understand` run and 63 in a plan run, so a large run is about 190 reader-numbered calls and about 60 planner calls; I split them by judgement as follows: reader 185 (read-more 40, reread 30, turns-left 25, read-first, task, area and parent-cards 20 each, answers 10), cards 68 (card-format 20, continue, flows and screens 15 each, repair 3), planner 44 (5 for each of 7 documents, gap 5, gap-repair and plan-repair 2 each), summariser 7, verifier 60. These are assumptions, not counts. (c) A reader call is multi-turn and its input grows each turn; the replay measures the first turn, so reader's share is **under**-stated. **Failure** is the larger of the Haiku unusable rate and the judge deficit (5 minus the judged mean, over 4) of the judged sample; reader first turns cannot be judged here, so they get a flat 25 percent placeholder (artefact, see 3). The score is share times failure.
