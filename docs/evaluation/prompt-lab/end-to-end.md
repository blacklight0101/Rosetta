# Prompt lab: end-to-end check on the rosetta-p10 stack (P10-11)

Card P10-11, 2026-11-14, GitHub issue #1389. Phase 10 (DEC-231). Three apps run end to end on Haiku 5.5 on a new stack, the way the evaluation of 2026-11-09 (P8w3) ran them, and compared with it. Spend: **$3.78** of the $6.00 slice (stack $2.52, judge $1.25); the shared lab ledger's settled total went from $24.454 to $25.707.

**Result: the tuned prompts run together, with two regressions to decide on.** All three journeys completed: no agent task ended failed, no HTTP 500, no `error` line in the server log. The three comparable journeys cost $2.35 against $2.65 (-11%) with about the same coverage, and the verifier retried far less (`claim.v6`). EV-100 and EV-108 are fixed. The judge, given the same extract rule on both sides, scores the P10 packages 3.0 (Asset Manager 3.0 to 3.0, Invoice 2.8 to 3.0, eShop 2.8 to 3.0). Two results go the wrong way:

- **Plan quality: more behaviour kept by no task card.** The eShop plan's `checks.md` lists 98 behaviour items of 13 cards that no task card keeps (P8w3: 14 items of 2 cards), and 7 data-model "dropped" entries were rejected by the answer schema (P8w3: none). Asset Manager went from 0 to 8 items; Invoice from 19 to 0. Likely causes: fewer, larger task cards (eShop 1.9 items per card against 2.5, 28 cards against 35, while the requirements rose from 25 to 30) and the gap-round change of EV-108 (P10-D6); the rejected entries have their own cause (P10-D7).
- **`read-more.v3` against the +15% per call of DEC-235 (c):** over on Asset Manager (the call after the reads +25.5%, the task's last call +17%), within on eShop (+10%, +14%). The owner decides between three options (section 4.1).

Eight defects are proposed as follow-up cards (section 6): one major (P10-D6), seven minor.

Only aggregate figures are written here. The Asset Manager and Invoice Generator workbooks, their cards, claims, file names and the runs' raw logs stay outside the repository (owner, 2026-11-14).

## 1. Method

**Stack.** A new Docker Compose project `rosetta-p10`, built from this branch's base, `develop` **`cb146766a`** (all of Phase 9 and the Phase 10 tuning merged), image `rosetta-p10:local` created 2026-11-14 11:50 UTC, empty volumes, 26 migrations applied. The app answers on `http://localhost:18098` (`127.0.0.1:18098`); the database port is not published. No other stack was touched.

**Key (DEC-228).** Compose got two env files, the main checkout's `.env` first and the stack's own file last, the order the P8w3 report describes (its own values win; the key comes only from the first file). The stack's file holds generated database passwords, a secret key and the bootstrap administrator, and sets `OPENAI_API_KEY` empty (no OpenAI in this card). A 5-token Messages call from inside the container answered 200 (status only). Note: the DEC-228 row says the main `.env` goes second; with that order the main file's own database and administrator values would win over the stack's. Proposed docs fix: P10-D5 (section 6).

**Caps.** The stack starts with the administrator defaults (run $0.50, user day $1.00, server month $10.00). P8w3 ran with a run cap of $4.00 and a user day cap of $10.00 (the $4.00 approvable of Asset Manager and eShop comes from the run cap, `journey-ceiling.ts`), so the same values were set; the server month cap was set to $5.60 as a hard guard for this card's slice. The first setting took an older run cap of $1.50 from the eval2 logs and was corrected to $4.00 only after the Asset Manager understand had started, so that journey was approved at $1.50 instead of $4.00; it spent $0.20, so nothing changed. Project caps stayed at the defaults.

**Journey (same as P8w3).** One test user created through the admin API (credentials outside the repository). Through the API, per app: create the project (zip upload, or the eShopModernizing URL at commit `63bc9ec4`), switch every role to Anthropic `claude-haiku-5-5` (reader `maxTurns` 12; the save raised parallelism 1 to 4 by itself, as in P8w3), scan, understand approved at the approvable amount, answers (one picked option, one typed answer), Deepen, answers, Plan setup with the same brief per app as P8w3 (`p8w3-plan.mjs`: recommended architecture and a .NET stack for Asset Manager and eShop, typed architecture for Invoice), plan, hand-off package. One app at a time. Same inputs: the same two zips (the Asset Manager snapshot hash is the P8w3 one) and the same eShopModernizing commit; the estimates came out identical to P8w3's.

**Invoice and EV-84 (same as P8w3).** The administrator set the user day cap to $0.10 around the understand start, so the journey was approved at $0.10, then restored $10.00. The driver answers pause 1 with Continue and pause 2 with Stop here, then resumes; P8w3 pressed the first two in the web, this card used the API for all.

**Not like for like: Asset Manager's answers.** The P10 Asset Manager understand asked no question (P8w3: 2, both answered), so its Deepen ran with no answers, while P8w3's Deepen had two. Its Deepen asked 2 questions (P8w3: 5); they were answered before the plan as on the P8w3 side.

**What changed since P8w3** (from the run manifests and `git log bbb696cd..cb146766a`): the Phase 9 fixes (EV-100 Continue raises the journey amount, P9-01; stop here has its own end, P9-03; interrupted readers, P9-04; EV-108 gap rounds build every requirement, P9-06; question merging, P9-13; data model against the decisions, P9-15; and the wording cards P9-02, P9-07..P9-12) and five prompt versions: `cards/card-format` v5 to v6 (P9-13), `planner/gap` v5 to v6 (P9-06), `planner/adr-model.v1` new (P9-15), `reader/read-more` v2 to v3 (P10-05, DEC-238) and `verifier/claim` v5 to v6 (P10-06). Phase 10 kept no other version (`cards.md`, `plan-docs.md`, `plan-gap.md`, `shared.md`, `verifier-summariser.md`).

**Measures.** From the saved run folders, the same way for both sides: `cost.json` (calls, tokens, cost), `cards/index.json` (cards, claims by status), `coverage.json` (read tokens over area tokens), `events.jsonl` (agent end states, RST codes, gap rounds), the transcripts (repairs: card repair, continuation, verifier retry, plan repairs, counted by their prompt text) and the package's `tasks.md` and `checks.md` (the P8w3 plan-stats tool). Running time is the run's start to end, queue apart.

**Judge of the package.** P8w3 had no judge score. The lab judge (`prompts/lab/judge.v1.md`, `lab/rubrics/planner.md`, Opus 5.5, through the shared ledger) scored the package of each P8w3 and P10 run the same way: the source is the Deepen's cards with a Supported claim, taken in turns over the card types, each cut at 1,200 characters, up to 40,000 characters. The answer is an extract of the package, at most 48,000 characters, built by one rule on both sides: the task cards' headings and fields first, then `prd.md`, `requirements.md`, `roadmap.md`, and `checks.md` cut at 8,000 characters. With that rule no eShop extract reached the cap (P8w3 42,062 characters, P10 37,954), so both judges saw every task card. A first judging put `checks.md` before the task cards; the P10 eShop `checks.md` had grown from 12.7k to 28.0k characters, so its extract stopped before any task card and the eShop scores were not like for like. eShop was judged again with the rule above (two more calls) and only those scores are reported; Asset Manager and Invoice fitted whole under the first rule (their `checks.md` are 1.5k to 6.2k characters) and were not judged again. Task-card bodies are left out on both sides (the judge says so in its actionability reasons), and the planner judge is advisory (`judge-sample.md`), so the score compares the two packages, it does not grade them.

**Decision for the owner.** Three options:

2. Keep v3 and add a cap on the lines one read-more turn may read (a new version, tuned in the lab against the real per-ask figure): bounds the Asset Manager case and keeps the wider reads; it costs a lab round and may lower coverage again.
3. Revert to `read-more.v2`: the per-call figures return to P8w3's; the wider reads and the eShop understand's +0.5 coverage points go.

Recommendation (builder): option 2, keeping v3 meanwhile, because the excess comes from the size of one ask's reads (484 lines on eShop, 396 on Asset Manager, against 226 and 276) and a line cap targets exactly that. P10-D1 carries it.

### 4.2 `verifier/claim.v6`: reasons and false "supported"

**Reason length.** v6 asks for a reason of at most 150 characters (refused above 300). In the runs the reasons are shorter than v5's but mostly above 150:

| eShop understand     | 1,482   | 209                       | 181                      | 154 of 159                                    |
| eShop Deepen         | 2,371   | 202                       | 179                      | 246 of 254                                    |
| Asset Manager Deepen | 307     | 214                       | 157                      | 54 of 56                                      |

The means include the screen-field checks' own short reasons ("the cited lines contain the field name ...", about 55 characters), which Rosetta writes without the model; the model's Rejected reasons average about 190 to 200 characters. Stored reasons over 300 characters: 2 in each eShop run of P8w3 (v5), 1 in each eShop run of P10 (the same claim in the understand and the Deepen, 316 characters). That reason was taken on the first answer with no retry, although v6's parser refuses a reason over 300: it quotes a masked secret, and the stored text carries the masking marker with its 95-character note (`shared/masked-value`). Since the parser took it, the text it checked was within 300; most likely the note was added by the masking of the stored text after the parse (not traced further). If so, it is not a refusal defect, only a stored reason longer than the limit; it is noted under P10-D2.
