The four questions of threat modelling: what are we building, what can go wrong, what are we doing about it, and did
we do a good job. The last one is answered by the tests named in each requirement and by the review dates above.

## 1. What we are building

A web application, reachable over the internet when hosted, behind which invited users sign in, download a public
GitHub repository at one commit, map it, let language-model agents read it through read-only tools, verify their
claims, and publish a static report. It stores accounts, sessions, encrypted provider keys and a cost ledger in
PostgreSQL, and snapshots and run output on a disk. Paid model calls run with the owner's server keys under caps
([architecture](../architecture.md)).

| A01 Broken access control                 | covered | sign-in on every route but the public ones; roles checked on the server; per-user scoping; CSRF and `Origin` checks (RF-1009, RF-1102, RF-1105)                                             |
| A02 Security misconfiguration             | covered | secure defaults (RNF-014); security headers and HSTS (RF-1013); configuration validated at start (RF-1305); local port on `127.0.0.1`                                                       |
| A03 Software supply chain failures        | partial | lockfile, pinned actions and base image, Dependabot, dependency review, `npm audit`, image scan (environments section 6, 8); the SBOM on releases and the GHCR image tags arrive with P1-55 |

| A05 Injection                             | covered | parameterised SQL (ADR-016); output never executed or rendered as HTML (RF-507); no shell                                                                                                   |
| A06 Insecure design                       | covered | this threat model; ADR-013; caps against cost abuse (RF-1106)                                                                                                                               |
| A07 Authentication failures               | covered | lockout, rate limits, password rules, session rotation and expiry, no self sign-up (RF-1100..RF-1103)                                                                                       |
| A08 Software or data integrity failures   | covered | commit-pinned snapshots with a hash (RF-121, RF-126); schema-validated files and settings; migration checksums (RF-1302)                                                                    |
| A09 Logging and alerting failures         | covered | security events in the application log (RF-009); audit trail (RF-1109); cap banner (RF-1106)                                                                                                |
| A10 Mishandling of exceptional conditions | covered | guards fail closed (RF-141); typed errors with codes, no stack traces in responses (RF-007)                                                                                                 |

Server-side request forgery is handled at TB1 (RF-127) and for the OpenAI-compatible base URL (RF-403, RF-1104): it is
set only with the user's key, must be `https` and must not resolve to a private, loopback or link-local address, checked
when saved and again when each call connects (DEC-112).

Tools considered and not adopted: Snyk Code (uploads source to a third party and adds nothing over CodeQL, `npm

deployment procedure (environments-and-delivery.md section 10).

## 6. Residual risks

- A prompt injection may still bias the wording of a card that cites real lines; the verifier's model step can be
  fooled the same way. The report always shows the cited lines, so a reader can check.
- Refused requests are bounded per client address (DEC-141), not in total: many addresses (a botnet, or the
  2^64 addresses of one IPv6 /64) can each write 31 refusal rows a minute, and beyond 10,000 addresses in a minute an
  address pushed out of the limiter starts a new minute when it comes back. The counts of minutes not yet ended are
  written when the server closes, but lost if the process is killed. The `http` access log entry of each response
  still holds the full request URL (up to Node's header limit), bounded by the log retention (RF-009), not by
  DEC-141.
- No multi-factor sign-in and no e-mail reset in release 1 (ADR-015); accounts are few and created by hand, and the
  teacher password is delivered only in the hand-in form.
- Losing `ROSETTA_SECRET_KEY` makes stored user keys unreadable; leaking it together with a database dump exposes
  them. It lives only in the host's secret store and the owner's git-ignored `.env`.
- The host provider and its staff are trusted with the database and the disk.
- The staging app (DEC-175, ADR-025) runs code from `develop` before the owner releases it, and it shares the
  PostgreSQL server with production. One server has one set of roles, so staging connects as `rosetta_app` and its
  migrate job as `rosetta_migrator`, the production roles: code on staging could technically reach the production
  database `rosetta`. Accepted for cost: separate roles would need a second server. Mitigations:
  only reviewed and verified cards reach `develop`; staging never creates or changes a role password and gets no
  server provider keys; its own `ROSETTA_SECRET_KEY` and administrator; the staging environment's credential is
  limited to the branch `develop`.
- On a host that offers a single database role, the server runs as the owner of `audit_events` and `cost_ledger`, so
  code in the server process could change or delete audit and ledger rows. The server logs a warning at every start
  in that case (DEC-140); the mitigation is to create `rosetta_app` (data-model.md section 6). The migrate step holds
  the migrator credential only while it runs, and so does whoever runs it by hand from a `.env` that holds it.
- A process on the owner's machine can read the local volumes; Rosetta does not defend against a compromised machine.
- The output writer checks every folder on the way to a workspace file for links, then checks the folder's real path
  again just before the temporary file is created, before the rename and before the append, but the file system
  offers no atomic "open beneath this folder" call in
  Node.js, so a short check-then-use window remains. Exploiting it needs a local process that can already write to
  the data folder, which is outside this threat model (see the previous point).
- An Ollama server at `host.docker.internal` counts as local even when Rosetta runs outside a container
  (DEC-174, DEC-118): in a developer run outside Docker that name could resolve to another machine, and private
  code would reach it without the cloud consent of RF-143. Both supported deployments run Rosetta in a container.
