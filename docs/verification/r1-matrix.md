## 2. Method

- **Tests.** The full Vitest suite ran locally on Windows against a disposable PostgreSQL 17
  (`ROSETTA_TEST_DATABASE_URL` set, `--maxWorkers=2`): 12711 tests, 12690 passed, 0 failed, 21 skipped (the
  Linux-only checks; they run in CI). The Playwright specs were listed for the `desktop-light` project, which runs
  every end-to-end test (231 tests in 55 files); they run in the three e2e jobs of CI. The two journeys of this card
  also ran locally against the test server (section 3).
- **Requirement to test.** A test counts for a requirement when its name or its `describe` title carries the id (a
  range such as `RF-620..RF-627` counts for each id inside it), as conventions section 7 requires. Skipped tests do
  not count. The counts per level come from the Vitest JSON report (by folder: `tests/unit`, `tests/integration`,
  `tests/e2e`) and from the Playwright list. One example per requirement is given, an end-to-end test where there is
  one; a search for the id finds the others. A count shows that tests name the requirement, not that every
  Given/When/Then scenario has its own test; the scenarios were checked by the verifier of each card.
- **Phase.** The phase is the row of the roadmap backlog that lists the id.
- **Manual checks.** Where a requirement's _Verification_ line asks for a hosted or owner check, the State column
  names it and its card. The manual checks of P1 are in [M1 matrix](m1-matrix.md) section 3.1 and are not repeated.
- **Whole.** `tests/integration/docs/r1-matrix.test.ts` (the checks are in `tests/support/r1-matrix-guard.ts`, and the
  test also runs them on bad matrices) fails when a release 1 requirement of the specification has no row; when the
  counts of a row are not three whole numbers; when a row's priority differs from the one in the specification; when a
  Must row has neither tests nor a card; when a State names a card that is in neither `docs/orchestration/tasks.md`
  nor the proposed cards of section 5; when an example names a file that does not exist or a line that is not inside a
  test (or a `describe`) whose title carries the id; or when a documentation set requirement of P3-22 is missing.

## 3. The release 1 journeys

The journeys of flows 1 and 7 ([process flows](../process-flows.md)) run end to end through the pages and the real
server (`tests/e2e/journeys/handoff-package.spec.ts`, steps in `tests/e2e/support/handoff-journey.ts`). Each signs in,
creates a project from the address `https://github.com/octo/webforms` (the test server's fake GitHub serves the
recorded snapshot of the C# fixture; the browser and the server reach no network), scans it, understands its Catalog
area, saves a planning brief in Plan setup, writes the package and downloads the hand-off zip from the page of the
plan run. Every model answer is a recording of the fake provider (ADR-008).

| Journey                                                                                               | The brief                                                                          | What the downloaded package must show                                                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| RF-604 RF-610 RF-611 from a GitHub URL to a downloaded hand-off package that follows the saved brief  | Parallel Change, the hosting layer typed by the user, the AI-assisted build method | the README's reading order; the migration decision is Parallel Change and the hosting decision names the typed technology; `AGENTS.md` is written; neither answered question is listed as a default; every requirement names a source card |
| RF-601 RF-605 RF-612 a brief saved with every default gives a package that lists the defaults it took | every default, saved from the last step                                            | the migration decision is the default Strangler Fig; no hosting decision; no `AGENTS.md`; the migration question is listed with its default in `open-questions.md`; every requirement names a source card                                  |

The two journeys differ only in the brief, so what the package says about the choices can only come from the saved
brief. Two mutations confirmed it: writing `AGENTS.md` whatever the brief says fails the second journey, and a
migration decision that ignores the brief fails the first. Both journeys also assert the project-context defaults
(RF-611: `context.teamSize`, `context.experience`, `context.deadline`, `context.keepIntegrations` and
`context.dataMigration` are listed in `open-questions.md`) and, in the first, that `AGENTS.md` names the typed
technology (RF-612); removing the context rows from the list, or the technology from `AGENTS.md`, fails them.

The journey of a project analysed from a zip (P3-42, `tests/e2e/journeys/zip-project.spec.ts`, steps in
`tests/e2e/support/zip-journey.ts`) zips the C# fixture inside the test (no committed binary), uploads it through
the Upload a zip tab and scans and understands its Catalog area with the fake provider. It checks that the report, the
specification and the cards of the run package each name the zip and the snapshot hash, that every citation opens a
Rosetta evidence page at the cited claim, and that no link of the run page, the report or the package leaves Rosetta
or names github.com. It also covers the second confirmation of a cloud role (RF-132), an upload replaced between two
runs (the second report names the new zip and hash, the first keeps its own) and the hand-off package. A Deepen and a
Resume on an uploaded fixture are in `tests/integration/application/upload-deepen-resume.test.ts`.

The journey of a project analysed from Excel workbooks (P3-52, `tests/e2e/journeys/workbook-project.spec.ts`, steps in
`tests/e2e/support/workbook-journey.ts`, workbooks in `tests/e2e/support/workbook-fixtures-journey.ts`) builds two
workbooks inside the test (no committed binary): `Pricing.xlsm` with a macro module, a shared formula, a table, a
validation list and a reference to `Discounts.xlsx`, the second workbook of the batch. It uploads them through the Excel
workbooks tab and scans and understands both with the fake provider, which replays
`tests/recordings/fake/understand-workbook-journey.json`. It checks that the report names the workbooks and the snapshot
hash, that every citation opens a Rosetta evidence page that names the workbook, the sheet and the cells of the cited
lines (and none for the dependency map and the macro module, which carry no cells), that the dependency map says
`Pricing.xlsm -> Discounts.xlsx`, that no link of the run page, the report or the package leaves Rosetta or names
github.com, and the second confirmation of a cloud role (RF-157). It also covers workbooks replaced between two runs (the
second report names the new hash, the first keeps its own), the hand-off package, and a zip that holds one of the
workbooks (rendered in place, citations labelled the same way). Two mutations confirmed it: changing the cells label of
`workbookCellLabel` and leaving the dependency map out of the rendered snapshot both turn the journey red.

The P3 exit criteria are covered as follows: the demo repository (the webforms-shop fixture) gives a whole package
from a saved brief in the documentation set journey of P3-22 (`tests/integration/journeys/documentation-set.test.ts`);
every requirement of the package names a source card in both journeys of this card and in that one; the HTML report
passes its WCAG 2.1 AA checks in the axe checks of RNF-010 (36 end-to-end tests in light and dark, at 1280 and 360
px).
