# ADR-029: Describe a prompt lab case by its inputs and keep one append-only spend ledger

**Date**: 2026-11-13
**Status**: Accepted (2026-11-13, DEC-231)
**Deciders**: Product owner (phase scope, DEC-231); builder P10-01 (design)

## Context

Phase 10 tunes each prompt on its own (DEC-231). Until now a prompt was measured only inside a whole run
(`npm run eval`, RF-305). The lab must send "the prompt's real messages" with different versions of the prompt over the
same inputs, so a case cannot be a recorded request (its prompt text is frozen into it). The phase has one budget of $50
with a stop for the owner at $40, shared by every card and by two builders working at once (DEC-229). Cases will be
written by P10-02 and later cards, so the format is built on by others. RF-1400..RF-1403, ADR-003, ADR-007, ADR-008.

## Options Considered

1. A case is a recorded request whose prompt part is replaced by the version under test.
2. A case holds the arguments of the run's message-building function for one agent task (the claim and its cited
   lines, the cards of an overview); a registry of targets renders them with any prompt file.
3. Keep spend only in each process's memory and in the provider's own account page.
4. Do nothing (measure prompts only end to end).

## Decision

We choose option 2, with a shared ledger file instead of option 3. A case is `{ id, expected?, split, input }`; `input`
is parsed by the zod schema of the target named by the set's `prompt` id. A target (`src/application/lab/targets/`)
supplies that schema, a function that calls the run's own builder with the prompt file under test, and the run's own
parser as the check of an answer. The lab composes the same guarded provider factory as `npm run eval`, and puts one
decorator on top of it that holds, settles and releases the cost of each call in `lab-out/ledger.jsonl`. The ledger is
append-only JSON lines of hold, settle and release; a process decides on the lines up to its own hold, so two processes
never pass a cap together, and a hold older than thirty minutes stops counting. The ledger file is `lab-out/ledger.jsonl`, or the absolute `.jsonl` path in the environment variable `ROSETTA_LAB_LEDGER`, which all Phase 10 builders set to the same file outside every checkout so the phase total does not depend on the worktree that runs the lab. The variable is required for every real provider: the $50 is one maximum for all builders together (DEC-231), so the lab refuses to start a real model without it; only the fake provider of the tests may keep the per-checkout default. `lab/config.json` holds the total
($50), the stop line ($40) and the cap of one invocation.

## Rationale

- Option 1 freezes the prompt text and the message wrapper in the case, so a new version cannot be rendered; the
  builders are already pure functions of a few inputs.
- The builders are the run's own code, so a message the lab measures is the message a run sends (RF-145 data blocks
  included).
- An append-only file needs no server and no lock; deciding on the lines up to one's own hold is order-independent
  across processes, the one property two concurrent builders need. A database ledger is not available to a script run
  from a worktree with Docker down.
- Option 3 cannot stop a second process; option 4 leaves the owner's phase goal unmet.

## Consequences

**Positive**

- A prompt version is tried over fixed inputs; adding a prompt id is one target file and one registry line.
- The phase total is one figure everyone can read and no process can pass.

**Negative**

- A target must be written per prompt id; agent-loop prompts (the reader) need their own targets: P10-01 wired none, P10-02 wired the first turn of three (see the amendment below).
- The ledger holds worst-case amounts while calls are in flight, so two processes can refuse a call the real cost would have allowed; a crashed process leaves a hold for thirty minutes.
- A call that failed after being sent is booked at the larger of the cost the budget guard knows and its held worst case, so the ledger may over-count it; only a call refused before sending is released.
- A hold is not renewed while a call runs: the lab refuses to start when the provider settings could keep one call longer than a hold lasts (30 minutes, counted as the budget guard counts its own reservation), and when a hold, a settle or a release cannot be written the invocation stops, so nothing is sent without a hold.

## Amendment (2026-11-13, P10-02): captured case sets, held-back rule and agent-loop prompts

- **Capture.** `npm run lab -- --capture` reads the `transcripts/` of a saved run folder and writes a case set with the inputs of the prompt's agent tasks, read back from the data blocks of their first messages. It stores no system prompt and no assistant text, writes no `expected`, makes no call, and leaves out a case that holds an e-mail address, a drive path, a home folder or a key-like string. The inputs of the planner and the summariser were themselves written by models earlier in the run (cards, plan titles); they are inputs here, never truth.
- **Format.** A set may hold `sources` (key, name, address, source commit or the hash of the upload, licence, run ids) and a case may name its source in `from`. The change is additive; `schemaVersion` stays 1.
- **Held-back rule.** At capture, the first `ceil(n / 3)` cases in the order of the SHA-256 of `<prompt id>:<case id>` are `held-back`. The rule reads no input, so it exists before any version is tried and cannot be tuned to a result; the tests recompute it for every committed set. (Replaced by the amendment of the P10 lab fixes below: the side is now decided by the input.)
- **Agent-loop prompts.** The lab does not run a reader loop. A reader case measures one turn: the conversation up to that turn is built from the case with the run's own prompt builders, and the single answer is classified (`reader/task`, `reader/area`, `reader/read-first`: whether it reads files with valid tool calls; `cards/card-format`: whether the answer after a replay of the reads the case holds is a valid card list). The case holds the area's file list and, for the card format, small excerpts of the files the run read. Options not taken: a short loop over files embedded in the case (needs a code map and an area per case, and a turn cap that changes what is measured); a recorded conversation (freezes the prompt text). The cost of this choice is that it does not measure the later turns of a loop; a tuning card that needs them adds a loop target.
- **Unpublished inputs.** Inputs of unknown origin or licence are never committed (DEC-03): `--capture --local` writes them to the git-ignored `lab/local-cases/`, and `--cases` reads a committed set first and a local one otherwise.
- **Not wired yet.** Every prompt family without a target is listed in the runbook (section 7); a tuning card wires its remaining family members first.

## Amendment (2026-11-13, P10-03)

The lab gets a judge (RF-1407, the judge and its per-family rubrics) and a judge check (RF-1408, the judge scored against hand-labelled and hand-scored samples). The decision above is unchanged; the judge adds, without changing the structure:
a judge call is one more provider call made through a second `LabCallGate` over the same guarded provider factory and the
same ledger object as the target's, so it is held, settled and capped like every lab call; its cost is kept in the case's
`judge` and not in the target's `costMicros`. The judge's inputs and the answer are untrusted, so three data block sources
(`lab_source`, `lab_answer`, `lab_label`) were added to the egress guard's list. A judge call that fails after it was sent
stops the invocation, because a failed call is booked at its worst case (a rejected key would otherwise be booked on every case).
The judge check is a mode of the same command, not a second entry point, so every real call still goes through `npm run lab`.

## Amendment (2026-11-13, P10 lab fixes): the split by input and first-try validity of a first turn

Two flaws were found before the P10-04 baseline, and the decision above is kept with these changes:

- **Held-back rule by input.** The earlier rule ranked the SHA-256 of `<prompt id>:<case id>`. The capture can take the same input (the same area, files and reads, or the same plan input) from two runs of one source, and the copies get different case ids, so one twin could be tuned on while the other was held back; the hand-built repair sets, ranked under their own prompt id, also split differently from the sets they were built on, so a held-back input could be tuned on through its repair. Both now hold: (a) the capture drops a case whose input equals an earlier case's input (the canonical JSON of the input: keys sorted at every level, no case id), before the split, and names it; and (b) the side is decided by the input: the distinct inputs of a set are ordered by the SHA-256 of their canonical JSON and the first third, rounded up, are held back, and a case built by hand on another (a repair case) takes the side of its base case. (a) alone leaves the cross-set leak of the repairs and any twin of a hand-written set; (b) alone keeps twins, which are measured twice, weigh twice in every rate and cost twice, and add nothing. (The cut of (b) at a third of each set's own inputs was replaced by the threshold of the next amendment.) The rule still reads no answer and no version of a prompt, so it exists before any version is tried; it no longer includes the prompt id, so the sets of different prompts over the same inputs (`reader/task`, `reader/area` and `reader/read-first`; `cards/card-format` and `cards/continue`; `planner/prd` and `planner/package`) hold back the same inputs, which keeps a tuned family of prompts from having seen any held-back input. The cost: the split of a set changes when an input changes (re-masking a secret moves its hash), and a set no longer has a fixed number of cases per run. The committed sets were rebuilt by these rules; the local sets (`lab/local-cases/`) are rebuilt by the owner's captures.
- **First-try validity of a first turn.** A first turn of the reader has no answer parser of the run and its answer may be tool calls, which the answer text does not show, so its first-try validity was always `true`, even for an empty answer. It is now `null` (not applicable) in `results.json`, the summary counts it only where it applies and prints `n/a` otherwise; `detail` and `usable` are the measure of a first turn. Not taken: judging the first turn from the text as `firstTurn` does, which would need the tool calls in the meter and would only repeat `usable`.
- **Masking at capture.** The capture masks every text of an input again with the run's secret masker, so a secret shape the masker learnt after a run was saved (the password after `sqlcmd -P`, RF-141) is masked in a case too.

## Amendment (2026-11-13, P10 lab fixes 2): a split that no other input decides, and escaped quotes

This replaces the cut of the held-back rule in the amendment above; dropping twins and taking a repair case's side from its base case stay.

- **The cut.** Holding back the first third of each set's own distinct inputs made the side of an input depend on the other inputs of the set: with hashes a < b < c < d, the set {a, b, c} holds back a and the set {b, c, d} holds back b, so b is tuned on in one set and held back in the other. Sets share only some inputs (`cards-flows` shares three of its nine with `cards-card-format`), and the owner's local re-captures can share any part, so a leak could appear without a sign. The side is now a function of the input alone: the SHA-256 of the canonical JSON of the input, read as a 256-bit number, is held back when it is below a third of the hash space. One input has one side in every set, whatever else the set holds, and a repair case, read through its base input, gets its base case's side by the same rule.
- **What it costs.** A set holds back about a third, not exactly, and a small set may have no case on one side: of the committed sets, `planner-api-contract` (3 cases), `planner-package` and `planner-prd` (4, the same inputs) and `planner-plan-repair` (4, built on `planner-package`) have no held-back case, and some sets hold back only one. Options not taken: a fallback that holds back the lowest input of a one-sided set (it depends on the set again, and so brings the leak back); a committed register of the side of every input (a second source of truth for a pure function); a threshold or salt chosen so that the committed sets come out two-sided (fitting the rule to the data). The capture **warns** and still writes a one-sided set, instead of refusing it: no change to the capture can move an input to the other side, the cases are still good for tuning and for the baseline (P10-04 runs on tuning cases), and a refusal would only leave the prompt with no set. A version of the prompt of a set with no held-back case cannot be kept (DEC-231) until more runs are captured; the runbook names those sets and the tests hold the list.
- **Inputs that hold a masked value.** The hash reads the masked text, so a change to the note of `prompts/shared/masked-value.v1.md` (the text that replaces a masked value) or to the rules of the masker re-hashes every input that holds a masked value and may move it to the other side. Such a change re-captures the sets, and the side of the inputs it touches is decided again, before any version is tuned on them.
- **Escaped quotes after `-P`.** The rule for the password of `sqlcmd`, `osql` and `bcp` read `\"` as a backslash value: inside a JSON string (`-P \"pw\"`, or an exec array `\"-P\", \"pw\"`) it masked the backslash and sent the password. The rules now follow the escaped-quote rules of P3-128: a quoted value opens with one to four backslashes and a quote and runs to the quote of the same kind and escape, so the other quote (`"it's"`) belongs to it; a bare shell word runs to a blank or a quote, a comma and a bracket included, which end a value only between the plain items of an exec array (`[CMD, sqlcmd, -P, pw]`).

## Amendment (2026-11-13, P10 masker gaps): every flag, the whole shell word, continued lines and literal values

The rule of the amendment above still sent a part of some passwords, and this closes those gaps; the decision is kept.

- **The whole word.** A shell joins bare and quoted parts into one word, so `-P Fake"pw"`, `-P Fake'pw'`, `-P "Fake"pw` and, inside a JSON string, `-P Fake\"pw\"` each give one password; the rule masked only the first part. The whole word is now the value and is masked with its quotes. On a shell line every quoted part joins the word (`-P Fake" pw"` too). When the command is inside a string (a JSON value, `bash -c '...'`: the quote before the tool's path opened it), a part that opens with that string's own quote and then a blank or a closing mark (`", "`, `"}`, `"]`) ends the string instead, so the rest of a JSON line stays readable; a quote with another escape still joins the word. A word that is one quoted value keeps its quotes (`-P "[MASKED:password]"`).
- **Continued lines.** A command split with a trailing `\`, `^` or backtick is one command line; the flag is now found on the continued lines too, within the same 512 characters.
- **Literal values and references.** A value that starts with `-` was left alone as a flag, so `-P -pw` was sent; it is masked now unless it is a one-letter flag (`-Q`). A `$` or `%` value is a variable reference and is left alone, unless single quotes make it a literal (`-P '$pw'`) or it is a `%` with no closing `%` and no `~` form (`-P %pw`). A reference is read whole: `$NAME`, `$$NAME`, `$env:NAME`, `$a.b`, `$1`, `$@`, `${NAME}`, `${{ secrets.NAME }}` to its closing `}}`, `$(command)` to its closing `)`, `%NAME%`, `%~1`. (An upper-case `'$NAME'` stays a placeholder in any quotes, as for every other rule.) Masking a reference would turn a variable of the code into a false finding that a password is written there. Not taken: masking every `$`/`%` value, which did that to `$env:SA_PASSWORD`, `${{ secrets.SA_PASSWORD }}`, `$1` and `%~1`.
- **Left alone only whole.** A reference, a masked value, a placeholder, a one-letter flag or a bare word of prose is left alone only when it is the whole shell word. When more of the word is joined to it (`-P $X"pw"`, `-P "$X"pw`, `-P to"pw"`, `-P [MASKED:password]"pw"`, `-P $(cat f)pw`), the whole word is masked: one marker, the same result the second time, and no guess at which part is the literal. So `-P "for"` and `-P [MASKED:x]pw` are masked; the note of the explained masker is read with its marker, so `-P pwd=Abc,pw` (the `pwd=` rule masks `Abc` first) is masked whole too.
- **Other flag shapes.** A quoted flag (`"-P" "pw"`), an exec array with a different escape on the value (`"-P", \"pw\"`) and `/P`, which `sqlcmd`, `osql` and `bcp` all accept (their documentation), are read too. `/P` needs a blank before and after it, is not followed by a path (`-o /P /out.txt`) and is not the argument of an option before it (`-i /P x.sql`); so `-o /P "pw"` is not read either, a gap develop has too.
- **Every flag of the command.** The first version of these fixes ended the match at the first `-P` after the tool, so a second password on the line (`sqlcmd -P "a" -S x -P b`, `[CMD, sqlcmd, -P, a, -P, b]`, or a real `-P` after `-Q "SELECT -Price"`) was sent. The rule is now a scan (`ScanRule`, scan-rule.ts) and not one pattern: from each tool name it reads the command token by token, at most 512 characters over the lines it continues, and reads every `-P` and `/P` it meets. A quoted argument of another option is skipped whole, so `-Price` inside `-Q "SELECT -Price"` is not a flag. A single-quoted argument has no escape (POSIX shells and PowerShell); a double-quoted one is read with backslash escapes, and when that reading would hold a password flag and the reading without escapes would not (a Windows path that ends in a backslash: `-o "C:\out\" -P "pw"`), it is read without them. A flag there is any word that starts with `-P` or `/P`, an attached value too (`-o "C:\out\" -Ppw`), and an argument between escaped quotes in a JSON string is read the same way (`\"C:\\out\\\"`, its first escaped quote, taken only when that reading holds no flag). So a skipped argument never swallows the `-P` after it. A quoted argument that holds a tool name at the start of a word (`"sqlcmd -P pw"`, `"[CMD, sqlcmd, -P, pw]"`, `-Q "exec xp_cmdshell 'bcp t out f -P pw'"`) is not skipped: the command stops there, the scan reads the commands inside the argument, and then the command around it goes on after the argument (unless a command inside already read past it), so neither the inner `-P` nor the outer one is lost. In a string around the command, the string's quote ends the command only when it does not open a quoted argument that holds no flag and is followed by another word: the quote before the tool may be a JSON key's (`{"a":sqlcmd -o "C:\out\" -P "pw","b":1}`), and the path's quote is not the end of that string. The command ends at a line end, an operator (`|`, `;`, `&`), `mysql` or `mariadb` at the start of a continued line (whose `-P` is the port: `sqlcmd -E \` continued into `mysql -P 3306`; as an argument, `-S mysql` or `-d mariadb`, they end nothing), another tool name, or the end of the string around the command. Not taken: a lookbehind from each `-P` back to a tool, which reads up to 512 characters again for every `-P`.
- **Masking twice.** A word left alone ends where a quoted value ends: at a blank, an operator, a bracket, a comma, or after an escaped closing quote at the quote of the string around it. So a value masked between quotes (`{"a": sqlcmd -P "pw"}`, `[sqlcmd -P "pw", 1]`, JSON nested twice, `bash -c 'sqlcmd -P \"pw\"'` in a JSON string) is left alone when the egress masks the text again; the first version masked the quoted marker again as a bare word and swallowed the rest of the line. An enclosed reference that does not close (`${{ secrets.X -Q x`, `$(cat f -Q x`) is left alone to the end of its word, and a value that starts with a comma (`-P ,pw`) is masked with it: only `-P,` with no blank is an exec array item.
- **Linear.** The next tool name is looked for after the place the last command was read to; the walk back from a tool name to a quote around the command stops there or at a delimiter (`,`, `[`, `;`, `|`, `&`, `(`), so each character is walked over once; a command that stopped at a quoted argument naming a tool goes on after that argument, not inside it; each step of a command reads at least one character; a quoted argument that does not close is not tried again with the same quote in that command; a value ends on its line. On the probes of #1404 (floods of tool names after a delimiter, of `-P`, of blanks after `-P`, of continuations, of backslash runs before a quote, at 0.5, 1 and 2 MB) the time grows linearly, and the masker takes 0.1 to 0.3 s for 1 MB of any of them on the build machine, by its load (the floods of tool names in quoted arguments of the final review too); the unit tests hold each to 2 s. Before, each of four rules read 512 characters after every tool name.
- **Regression corpus.** `tests/fixtures/guards/sqlcmd-corpus.json` holds the inputs of the verifier's probes of #1404 (invented values only) with develop's results; a test holds, for the plain and the explained masker, that no part develop masked leaks, that a second masking changes nothing, and that every input develop left alone stays unchanged.
- **Known gaps.** A `-P` more than 512 characters after the tool, an exec array with no tool name, an escape of more than four backslashes (JSON nested three or more times), a YAML folded block (no continuation mark), a YAML block list (`- -P` on one line and `- pw` on the next, as in some docker-compose healthchecks), `/Ppw` with no blank, `-o /P "pw"`, an enclosed reference that does not close joined to a literal (`$(pw`), and a command built by string concatenation in code: none is read, as on develop.
- **The sets.** No committed set changes under the new rule (the tests mask every text of every case again). A local set captured before it may hold a password the rule now masks, and re-masking moves the hash of that input, so its side may change: rebuild the local sets with the same capture command before any tuning on them.
- **Two checks of the split.** `heldBackKey` threw nothing on a key that is not a SHA-256 and called it `tune`, which would have hidden a fault of the capture; it now throws. `--compare` of two runs whose cases have no held-back case now prints a warning, since such a comparison cannot keep a version (DEC-231).
