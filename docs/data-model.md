Rosetta keeps its data in two places (DEC-65, [ADR-016](adr/ADR-016-postgresql-and-files.md)):

- **PostgreSQL** holds what needs transactions, ownership and sums across users: accounts, sessions, encrypted
  provider keys, projects and their settings, the run index, the cost ledger, server settings and the audit trail
  (section 4).
- **The data folder** (`ROSETTA_DATA_DIR`, a volume) holds large trees of files: the shared snapshot cache, one
  workspace per user with the run folders, and the daily logs (sections 2 and 3).

This document is the contract between the domain model ([architecture](architecture.md) section 5), the adapters,
the web UI and the builders. The database never stores file contents; files never store passwords, sessions or keys.

## 1. Conventions

| Topic          | Rule                                                                                                                                                                                                                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Formats        | structured data is **JSON** (UTF-8, no BOM, LF, two-space indent); append-only logs are **JSON Lines** (`.jsonl`, one object per line); human documents are **Markdown**; cards are Markdown with a **YAML header**; project settings are JSON in the database (DEC-25, DEC-43, DEC-65)       |
| Schema version | every JSON and JSON Lines file, every card header and every settings document carries `schemaVersion` (an integer per file kind, starting at 1). Readers accept the current and the previous version; a newer version than the reader knows is refused with an error code (DEC-43, section 7) |
| Validation     | every file is parsed with its zod schema when read; nothing is cast. Schemas live in `application` (domain files) or `infrastructure` (adapter files); the domain imports no third-party package (ADR-009)                                                                                    |
| Field names    | `camelCase`; ids and enum values exactly as defined below; no abbreviations except `id`, `sha`, `url`                                                                                                                                                                                         |
| Enumerations   | strings from the canonical state lists in [architecture](architecture.md) section 5 (`ClaimStatus`, `CardType`, `OpenQuestionState`, `AgentTaskState`, `RunEndState`, `MapLevel`, `Confidence`) or listed in this document; never integer codes                                               |
| Times          | instants are ISO 8601 UTC strings with milliseconds and `Z` (`2026-10-10T14:03:22.415Z`), taken from the `Clock` port; durations are integer milliseconds with an `Ms` suffix                                                                                                                 |
| Paths          | relative to the **repository root** of the snapshot (not to the subpath), forward slashes, no leading `./`, case as in the repository (RF-124, RF-125)                                                                                                                                        |
| Citations      | `path:startLine-endLine`, 1-based, inclusive, `startLine <= endLine` (ADR-005); stored as an object `{ path, startLine, endLine }` in JSON and as the string form in Markdown                                                                                                                 |
| Money          | cost is stored as an integer `costMicros` (millionths of the price-table currency, USD per DEC-54) plus `currency` (ISO 4217); never a floating-point amount. Displays round to 4 decimals below 1 and to 2 above                                                                             |
| Tokens         | integers `inputTokens`, `outputTokens`, `cachedInputTokens`; `usageSource` is `reported` or `estimated` (RF-421)                                                                                                                                                                              |
| Determinism    | files that must be byte-identical for the same input (`codemap.json`, `cards/index.json`) sort arrays by a stated key and objects by key, and contain no times (RF-106)                                                                                                                       |
| Atomic writes  | JSON and Markdown files are written to a temporary name in the same folder and renamed; JSON Lines files are appended one complete line per write. A reader ignores a truncated last line and logs a warning                                                                                  |
| Secrets        | every file passes through secret masking before it is written; no file ever holds an API key, a token or a header value (RNF-003, RF-141); in the database, keys are stored only encrypted and passwords and session ids only hashed (ADR-015)                                                |
| SQL names      | tables and columns `snake_case`, tables plural; primary keys `id`; foreign keys `<table singular>_id`; times `timestamptz` named `*_at`; money `bigint` named `*_micros`; enumerations are `text` with a `CHECK` constraint; conventions.md section 2                                         |
| Ownership      | every table with user data has a `user_id` column, and every repository query filters on it (RF-1105)                                                                                                                                                                                         |
| Line endings   | LF in every file Rosetta writes, on every operating system                                                                                                                                                                                                                                    |

An atomic write on Windows can meet a reader: the operating system refuses a rename onto a file that another
handle has open (`EPERM`, `EBUSY` or `EACCES`). The rename is tried again up to 12 times, a little later each
time, while the temporary file is there (`src/infrastructure/files/rename-when-free.ts`, P3-59); any other failure
surfaces at once.

## 2. Folder map

Everything Rosetta writes to disk is inside the data folder `<data>` = `ROSETTA_DATA_DIR` (RF-005, RF-1305).
Folder names come from ids, never from request text.

```text
<data>/
  sources/
    <owner>__<repo>@<sha>/            one snapshot per commit, shared by all users, read-only (3.3)
      snapshot.json
      files/...                       the repository tree at that commit
  logs/rosetta-YYYY-MM-DD.jsonl       application log (3.14)
  users/<userId>/                     one workspace per user (RF-1105)
    projects/<projectId>/
      codemap.json                    code map of the last scan (3.4)
      scan-summary.md                 readable scan summary (3.5)
      answers.md                      answers to open questions (3.16)
      planning-brief.json             planning brief for plan (3.20)
      runs/
        <runId>/                      one folder per run (3.6..3.15)
          manifest.json
          events.jsonl
          provider-calls.jsonl
          egress.log.jsonl
          cost.json, cost.md
          cards/<TYPE>/<CARD-ID>.md, cards/index.json
          invalid-output/<agentTaskId>.txt  raw answers of a task that ended InvalidOutput (3.7)
          spec.md
          data-model.md               legacy data model of the ENT cards, only when the run has one (3.8)
          overview.md, overview.json  the overview of the application (3.8a)
          coverage.json, coverage.md
          transcripts/<agentTaskId>.jsonl
          report/                     static report (RF-500..RF-506)
          handoff/                    hand-off package (RF-600..RF-699)
      exports/<runId>.zip             reserved; the zip export is streamed and writes nothing here (RF-008, architecture `ExportZip`)
```

`<userId>` and `<projectId>` are the UUIDs of their rows (section 4). `<runId>` is `yyyyMMdd-HHmmss-<stage>` in UTC
(for example `20261010-140322-understand`), unique in the project; a second run in the same second gets the suffix
`-2` (RF-003). The project cost ledger moved from `cost-ledger.jsonl` to the `cost_ledger` table (3.13).

`src/application/projects/project-settings.ts`; every field is required except the lists and values with no default
(`budget.prices`, `budget.roles`, `scan.areas`, `contextTokens`, `temperature`, `maxTurns`), so a stored document is
complete. A save returns every problem with its dotted field and one of: RST-1001 (unknown provider kind, or a role
naming a provider the project does not define), RST-1002 (a role missing or without a model), RST-1003 (a cap or
price below zero), RST-1004 (a `baseUrl`), RST-1006 (any other value or key that is not allowed); RST-1005 is the
code of the refusal as a whole; a save whose `If-Match` version is no longer the stored one answers RST-1007 with status 409. A new project takes `templates/project-settings.json` with `scan.ignoreRules` from
`templates/ignore-rules.txt`, the provider and model of each role from the server setting `defaultRoles` where set,
only the providers its roles use, and `agents.parallelism` 1 when the reader is Ollama (DEC-106). The numbers in
`templates/project-settings.json` (run cap, confirmation threshold, output limits, turns, timeouts) are
the owner's confirmed defaults (DEC-116); the numeric fields have the allowed ranges of the table above (DEC-117) and a
value outside a range is RST-1006; the placeholder model is `gemma4:e4b`, the best reader measured
so far (providers.md 2.6), until the reader spike (P1-47) decides.

### 3.2 `.rosettaignore`

Changed 2026-10-11: the rules are the `scan.ignoreRules` field of the project settings (3.1). Gitignore syntax,
matched against repository-relative paths (RF-140). A `.rosettaignore` file committed in the analysed repository is
also read and joined to the setting; it can only add exclusions, never lift the setting's rules or the built-in deny
list (DEC-109). The default template lists common secret and binary
patterns (`*.pfx`, `*.key`, `*.env`, `appsettings.*.json` with secrets, `*.mdf`, images and archives).
No `schemaVersion`: the format is the standard gitignore syntax.

### 3.3 Snapshot cache: `sources/<owner>__<repo>@<sha>/`

|         |                                                                         |
| ------- | ----------------------------------------------------------------------- |
| Purpose | the legacy code at one commit, downloaded once and read-only afterwards |
| Writer  | `GitHubSnapshotFetcher` only, once per commit (RF-122)                  |
| Readers | scanner, agent tools, verifier, through `RepositoryReader`              |
| Spec    | RF-120..RF-126, RF-005                                                  |

- The folder name is lower case (`<owner>__<repo>` as GitHub names are case-insensitive), so a cached commit is
  found however the URL was typed; `snapshot.json` keeps GitHub's spelling.
- The archive is extracted into `sources/.partial-<uuid>/` (id from `IdGenerator`); an entry with an absolute path or
  a `..` segment stops the fetch with `RST-1906` and the partial folder is deleted (RF-122, ADR-019); link entries are
  skipped and counted (RF-127). When extraction and hashing finish, the folder is renamed to its final name, so
  a half-finished download never looks complete. Leftover `.partial-*` folders are deleted at start-up.
- The repository tree goes under `files/`; `snapshot.json` sits next to it, outside the analysed tree.
- After the rename, files are marked read-only where the operating system allows it; the reader opens files
  read-only in any case.
- Two fetches of the same commit take an in-process lock per `owner/repo@sha`; a rename that fails because the
  target exists deletes its own partial folder and uses the existing snapshot (DEC-112).

`snapshot.json`:

| Field                     | Type    | Notes                                                                                               |
| ------------------------- | ------- | --------------------------------------------------------------------------------------------------- |
| `schemaVersion`           | int     | 1                                                                                                   |
| `url`                     | string  | canonical `https://github.com/<owner>/<repo>`                                                       |
| `owner`, `repo`           | string  | as returned by the GitHub API (case preserved)                                                      |
| `commitSha`               | string  | 40 hex characters                                                                                   |
| `resolvedFrom`            | string  | the ref that was asked for, or the default branch when the URL had none                             |
| `downloadedAt`            | instant |                                                                                                     |
| `fileCount`, `totalBytes` | int     | regular files under `files/`                                                                        |
| `skippedLinks`            | int     | symbolic and hard link entries skipped during extraction (RF-127)                                   |
| `snapshotHash`            | string  | `sha256:` of the sorted list of `path` + file SHA-256 pairs; recorded in each run manifest (RF-126) |
| `licence`                 | string  | SPDX id reported by GitHub, or `unknown`                                                            |

**Kinds of snapshot (RF-130, RF-152, RFC-004 section 4.1, RFC-005 section 4.1, P3-36, P3-43).** A snapshot is a GitHub commit, an uploaded zip or rendered Excel workbooks. The
record says which with `kind`, and a record without `kind` is a GitHub one: every record written before uploads
existed, and every record the GitHub fetcher still writes, so a GitHub `snapshot.json` is byte-identical to what it
was. The fields above are the GitHub record. An upload record holds `kind: "upload"` and only these fields; a record
that has `kind: "upload"` and any GitHub field (`url`, `owner`, `repo`, `commitSha`, `resolvedFrom`,
`downloadedAt`, `licence`), a missing or empty `fileName`, or a `kind` that is none of the three is refused with `RST-1906`
when it is read. The licence of an upload is `unknown`; it has no field. The folder name of an upload is
`upload__<project id>@<first 16 hex of snapshotHash>`. `PUT /api/projects/:id/source` writes it (P3-38): the zip is streamed to a `.partial-<uuid>` folder under `sources/`, unpacked into its `files/`, hashed, and the folder is renamed into place and made read-only; the zip itself is deleted.

| Field                     | Type    | Notes (upload record)                                                                                                                                             |
| ------------------------- | ------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schemaVersion`           | int     | 1                                                                                                                                                                 |
| `kind`                    | string  | `upload`                                                                                                                                                          |
| `fileName`                | string  | the file name as sent, with its `.zip`; not empty                                                                                                                 |
| `uploadedAt`              | instant | when the upload finished                                                                                                                                          |
| `fileCount`, `totalBytes` | int     | regular files under `files/`                                                                                                                                      |
| `skippedLinks`            | int     | entries skipped during extraction (RF-129)                                                                                                                        |
| `snapshotHash`            | string  | as for GitHub; the identity of the upload, recorded in each run manifest                                                                                          |
| `workbooks[]`             | list    | optional (RF-152, P3-43): the workbooks the zip held, one entry each as in the workbook record below; absent when it held none, and an empty list reads as absent |

**Workbook snapshot (RF-152, RFC-005 sections 4.1 and 4.4, P3-43).** A third kind. The record holds `kind: "workbook"`, `uploadedAt`, `rendererVersion`, `workbooks` (at least one entry), the tree counts and `snapshotHash`, and no GitHub field and no `fileName`; it is parsed strictly, so a record that mixes the kinds, or whose entry lacks a field or holds an extra one, is refused with `RST-1906` when it is read. Its identity is the hash of the rendered tree, so a new renderer version can give a new hash for the same files. The folder name is `workbook__<project id>@<first 16 hex of snapshotHash>`; a workbook record under any other kind of key, and any other record under a workbook key, is refused with `RST-1906`. The licence is `unknown`; it has no field. The files that make the tree are written by the reader and renderer cards (P3-44, P3-45).

| `kind`                    | string  | `workbook`                                                                                                                                                                                                                                                     |
| `uploadedAt`              | instant | when the upload finished                                                                                                                                                                                                                                       |
| `rendererVersion`         | string  | which renderer wrote the tree; not empty (`2` heads a region of `formulas.md` with the table and column it fills, P3-94; a snapshot rendered before keeps `1`)                                                                                                 |
| `workbooks[]`             | list    | one per file, at least one: `fileName` (as sent, not empty), `folder` (in the tree), `sizeBytes`, `sha256` (`sha256:` and 64 hex, of the file as sent), `counts` `{ sheets, nonEmptyCells, formulas, macroModules, macrosSkipped }` (whole numbers, no others) |
| `fileCount`, `totalBytes` | int     | regular files under `files/`                                                                                                                                                                                                                                   |
| `skippedLinks`            | int     | entries skipped (0 for a set of workbooks)                                                                                                                                                                                                                     |
| `snapshotHash`            | string  | as for GitHub, over the rendered tree; recorded in each run manifest with the renderer version                                                                                                                                                                 |

(`codemapHash`, SHA-256 of the file) goes into the run manifest.

Rules for `areas[]` (RF-104, added with P1-20):

- A file in the `config` areas of the settings (3.1) goes to the first area whose patterns match it (gitignore syntax); every
  other file is grouped automatically. Links never join a configured area.
- Automatic grouping: each top-level folder is one area (`name` is the folder path; files at the root form `(root)`).
  A folder over `scan.areaTokenBudget` is split by sub-folder; its own files stay in an area named after the folder.
  Files that a language pack links (a page and its code-behind) are put in the area of the linking file, with
  `origin` `references`, when together they fit the budget.
- A group still over the budget is cut, in path order and never between linked files, into parts named `<name>#1`,
  `<name>#2`, and so on. A single file larger than the budget is the one allowed exception and forms an area alone.
- An automatic name gets ` (auto)` appended until neither it nor its numbered parts equal a configured name or another
  area's name; two configured areas whose names (parts included) collide are refused.
- `mapLevel` of an area is `symbols` when at least one of its files is `symbols`, else `coarse`.
- Every text taken from a repository (file paths, area names, `subpath`, SQL text, symbol and entity names, link
  symbols) is passed through the secret masker before it is written (RF-141); `sqlStatements[].text` is cut to 500
  characters after masking. The scan keeps up to 1 536 characters of a statement for the masker, and every cut the
  scan makes (that window, and the 4 000-character line limit) falls between words: when it would fall inside a run
  without white space, the whole run is dropped. Every masker rule matches inside one such run (keys, connection
  URLs, `password=value`) or runs to the end of the text once its keyword is seen (key blocks, quoted values,
  `;Password=`, a CDATA value of an XML password element); the one exception is the XML password element without
  CDATA, whose value may start after blanks, may hold spaces and ends at its closing tag on the same line, so a cut
  that falls between the opening tag and the closing tag drops the open element with its value (P1-112, P1-124). So a secret whose end was cut away (for example the `@` of a connection URL) is never kept in part.
  A wider window alone would not be enough: masking shortens the text, so the cut end can reach the first 500
  characters. The 500-character cut after masking falls between words as well, so it never leaves half a marker or
  a bare `scheme://user:` behind. A statement with no white space before a cut keeps an empty text.
- File paths and area names that masking changed and that then share one masked form get `~1`, `~2`, ... in the
  code-unit order of the real names, so two files that differ only by a secret stay distinct. The suffix is an
  ordinal, not a hash, so it cannot confirm a guessed secret. If a masked or suffixed name still equals another name, the map
  is refused (`duplicate-file` or `duplicate-area-name`) and nothing is written.
- Reading `codemap.json` checks the 40-character lower-case `commitSha`, `endLine >= startLine` of a symbol, and
  that each area's `files` are sorted.
- Routes found by a language pack are not written to the code map in this release (3.4 has no field for them).

and `spec.md` are written together: each file's previous content is read first, and when a write is refused or fails
part-way every file already written gets its previous content back and a file that did not exist is removed
(RNF-002); a file that cannot be put back is logged and the original refusal is returned, even when the log entry
itself cannot be written. The writer does not lock: card writes to one run folder must be serialised by the caller,
because two writes at once would each take the other's half-written files as the previous content. An understand run
rewrites the whole set after each task ends (the cards of every ended task, ids given in area order), one write at a
time per run folder, so a run that stops keeps the cards of the tasks that ended (P1-33). Every claim passes the citation check
(verifier step 1) before it is written: a citation of a path that is not a file of the code map, a range whose start or end
is not a whole number or that breaks `1 <= start <= end`, or a range that ends after the file's last line, makes the claim `CitationInvalid` with the reason in its verdict
(`{ step: citation, model: citation-check }`); a claim that passes stays `Proposed` until the judgement step (DEC-103).

judges each claim still `Proposed` with the `verifier` role and the set is written once more: the claim becomes
`Supported` or `Rejected` with the model's one-line reason, or `Unverified` with the reason it could not be judged
(an answer unreadable after one retry, cited lines that cannot be read or are too long, a failed call, or a cap
reached before it was judged, RF-304), in a verdict `{ step: judgement, reason, model: <the verifier's model>, at }`.

`verify.claim.judged`.

double-quoted scalar, so model text cannot add a key. `cards/index.json` has `schemaVersion` and `cards`, and its
`claimCounts` always lists all five statuses.

When no valid card is left after the follow-ups (up to two repairs, or continuations of a cut-off answer), the task ends
`InvalidOutput` (RST-1300). The raw answers of a task that ended `InvalidOutput`, or that kept cards but dropped something, are
saved, masked, in `invalid-output/<agentTaskId>.txt`, separated by `=== attempt n ===` lines; those of a task that was run again
(RF-208) are all kept, the first run's first. A task that ends with no usable card is run once more from the start with a fresh
conversation (an area that met its context limit, in two halves); the retry's transcript and calls carry the id
`<agentTaskId>-retry`, or `<agentTaskId>-retry-1` and `-retry-2` for the halves (3.15).

`{ schemaVersion: 1, tasks }` where each task is `{ agentTaskId, area, state, turns, withoutCards, cards, coverage }`: `state` is
how the task ended (an `AgentTaskState` after `Running`), `cards` its cards with their ids and every claim with its status
and verdict (the same data as the card files' headers), `coverage` its entry of `coverage.json`. Tasks keep the area order.
A `FLOW` card keeps its `flow` and the `target` and numbered `branches` of its steps, a `SCRN` card its `screen`, and the
coverage its `surface` (with `incompleteFlows` when set), so a resumed run keeps them whole (RF-260, RF-261, P2-19).
A card keeps its `mergedFrom`, `mergedAreas` and `note`, and the coverage its `failure` and `note`, so a resumed run reports the
same coverage failures and merged areas as an uninterrupted one (RF-206, RF-208, RF-250, P2-28).
The file is masked like every file Rosetta writes. A resume keeps a task when the manifest lists it `Done`, `TurnLimitReached`
or `InvalidOutput` and this file holds its result for the same area; any other task, and a finished task without a result,
runs again. New cards are numbered after the kept ones, so an id once given never moves. A file that is not a version 1
results file is refused with RST-1309.

### 3.8 `spec.md`, `data-model.md`, `coverage.json`, `coverage.md`

- `spec.md`: opens with `## Overview`, the overview of 3.8a (once the run has one), and, when the run has cards, `## Verification summary` (RF-303, P2-03): `Supported share: <n> of <m> claims (<p>%).` and a table with one row per area, in the order of the run, and a last row `All areas`, whose columns are the claims of each status (`Proposed`, `CitationInvalid`, `Supported`, `Rejected`, `Unverified`, in the order of the vocabulary), their total and the supported share. The share is the `Supported` claims over the claims of every status, so a rejected, invalid or unverified claim lowers it; it is `n/a` for an area or a run without claims. The same section is in `report/report.md` and `report/report.html` (computed from the claim counts of `cards/index.json`, by `src/domain/cards/verification-summary.ts`).
  Then come the cards per area as one readable specification with links to the card files and, for every citation, to the cited lines on GitHub (RF-204, RF-125). Areas and cards keep the order of the run (area and appearance order); every claim
  is listed with its status, rejected ones included. The run summary of a re-run with answers (RF-241) adds `## New cards` and `## Changed cards` after the areas, each only when it has cards: a card is new when the earlier run that raised an answered question has no card of the same area, type and title, and changed when it has one whose claim texts differ. A last section, `## Areas without cards`, names every area whose
  reader ended `Done` without a card (suspicious: the answer must say `{"cards": []}` explicitly), so it is seen (P1-33). After the areas, and only when the run has cards of the type, come `## Flows` (each `FLOW` card with its link, trigger, outcome, generated sequence diagram and its steps with their claim status), `## Screens` (the generated screen map first, which matches a leads-to route to the `SCRN` card with that route, then each `SCRN` card with its link, route, roles and links) and `## Data model` (a link to `data-model.md` with the number of entities) (RF-263, P2-22). Diagrams are made by `src/domain/diagrams/` from masked card text.
- `data-model.md` (RF-262, P2-22): written with the cards when the run has at least one `ENT` card, never otherwise; a re-run into a folder that already holds it removes it when the cards no longer have an `ENT` card (P2-33). `# Legacy data model`, the generated entity-relationship diagram, `## Entities` (each `ENT` card once, in card id order, with a link to its card file, summary, area, confidence, `Merged from:` when consolidation merged cards into it, and its claims as the fields, keys and relations the card states, each with status and citations, rejected ones included) and `## To confirm`. `ENT` cards hold claims, not structured fields or relations, so the diagram shows the entities and the relations their claims state (P3-34): a `Supported` claim of an `ENT` card that names another `ENT` card by its title, as a whole word, draws one relation between the two (one per pair, from the first such claim, labelled "stated by <claim id>"); a `Rejected`, unverified or not yet judged claim draws none. The cardinality is never guessed: the relation is drawn dotted with an open end, and listed under `## To confirm` as "cardinality unknown". When no claim states a relation, the list says that relations are not recorded.
- `coverage.json`: `{ schemaVersion: 1, areas }` where each area is
  `{ area, files: [{ path, read: [{ startLine, endLine }] }], tokens, readTokens, readTokenShare, failure?, note? }`, where `note` (RF-206, RF-243) is present only for an area worth a remark: `not read` (its agent answered without reading any file of the area), `no readable file in the area (only binary or ignored files)`, `no application logic` (every file of the area is third-party code, so it writes no open question), the reasons joined by `; `, and `failure`
  (RF-208) is present only for an area whose task gave no usable card, in a few words with the code (`invalid output
(RST-1300)`); feeds the web UI
  coverage map (RF-1005, through `GET /api/runs/:runId/coverage`, which lists every file as read or not read) and the report. Areas keep the order of the run and list only tasks that ended; `files` is
  every file of the area in the area's order, `read` the line ranges the task's tools returned (a read, the lines of
  grep matches, the statements of a code map entry), cut to the file, sorted and merged, empty for a file not read;
  lines of files outside the area are not counted. `tokens` is the area's estimated tokens, `readTokens` each file's
  estimated tokens in proportion to its lines read (rounded per file, then summed), `readTokenShare` their ratio from 0
  to 1 with four decimals (0 for an area without tokens). It holds no times, so the same coverage gives the same bytes. Rewritten with
  the cards after every task that ends (P2-04). Each area also has `surface: { flowsMarked, screensMarked, flowCards,
screenCards, incompleteFlows? }` (RF-260, RF-261, RF-263, P2-19, P2-20): whether the code map marked the area for flows (it holds an entry
  point) and for screens (it holds a page, form, view or template), and how many `FLOW` and `SCRN` cards the task
  wrote, and `incompleteFlows` how many of those flows have a step that is `CitationInvalid` or `Rejected` (worked out again whenever the file is written, so after the judgement step too); the keys are absent from coverage written before they existed.
- `coverage.md` is its readable form (RF-230): a `## Run summary` table with, per area and for all areas, the files
  read of the files listed and the percentage of area tokens read, then one `## Area: <name>` table per area with each
  file and its read lines or `not read`. When an area failed (RF-208) a `## Failed areas` list follows the run summary, and when an area has a `note` a `## Notes` list follows that.
  A `## Flows and screens` section follows it, one line per area: `<n> flow card(s) (<n> incomplete); <n> screen card(s)` (the incomplete count only when above 0), or `no flows
found` / `no screens found` for an area the code map did not mark for them, so the absence reads as a finding and
  not as a gap (RF-261).

### 3.8a `overview.md` and `overview.json` (RF-264)

When an understand run has ended its readers, the judgement and the merge of duplicates, the `summariser` role writes the
overview of the application from the cards whose citations passed (a claim passed unless its citation check failed or the
judgement rejected it; open questions are not used). The two files are written with the cards, in the same atomic write
as `spec.md`, which opens with the same text under `## Overview`.

- `overview.json`: `{ schemaVersion: 1, state, notice?, sections, notCovered, questions }`. `state` is `full` (written from
  the cards), `thin` (too few cards to explain the application: fewer than 3 cards that passed, or cards from fewer than
  half of the areas the run was asked to read or that are third-party; when the owner chose some areas and left others of the
  application's own code out, the areas to compare with are the chosen ones; the summariser is not asked when there are
  fewer than 3 cards) or `unavailable` (the run was stopped, or the call failed or was refused by a cap). `notice` is present
  for `thin` and `unavailable` and says why and what to do next; a `full` overview of a run of chosen areas also has one,
  saying how many areas were read out of how many the scan found and that reading more gives a fuller picture. `sections` holds only the sections that have a statement,
  in the order `application`, `users`, `features`, `screens`, `data`, `integrations`; each is
  `{ id, statements: [{ text, cards: [{ id, type }] }] }` with at least one card per statement: the summariser's
  statements that name no card, or only cards it was not shown, are dropped (and counted in the log). `notCovered` lists,
  in the code map's area order and in plain sentences made by Rosetta (not by the model), every area that gave no
  card that passed: third-party code, not selected for the run, reader not finished, reader failed, or no card passed.
  `questions` links each open question card (`cardId`) to the first section that links a card citing a file the question
  cites; a question that shares no file with the overview has no entry.
- `overview.md` is its readable form: `# Overview`, the notice as a quotation, one `##` heading per section with one list
  item per statement and its card links, a line `Open questions about this section` where the section has questions, and a
  last `## What was not covered`. All model text is escaped (RF-507). The report (`report.md`, `report.html`) opens with
  the same overview, its card links one folder up.
- The run page reads it through `GET /api/runs/:runId/overview` (`{ overview }`, `null` when the run wrote none) and shows
  it first, before the open questions.

### 3.14 Application log: `<data>/logs/rosetta-YYYY-MM-DD.jsonl` and standard output

Line: `{ schemaVersion, at, level, logger, message, code?, runId?, agentTaskId?, callId?, data? }`; `level` is
`debug`, `info`, `warn` or `error`; `userId` is added when a request or run has one. The same entries go to standard
output as JSON lines at `ROSETTA_LOG_LEVEL` and above. One file per UTC day; files older than `ROSETTA_LOG_RETENTION_DAYS` (default 14) are deleted at
start-up and daily (RF-009): a file is deleted when its UTC day is more than that many days before today, and
only files named `rosetta-YYYY-MM-DD.jsonl` are touched. Every entry passes the secret masking: `logger`,
`message`, the ids and every key and string inside `data` are masked as `[MASKED:<kind>]`, with line breaks kept.
A `data` key at any depth whose name contains `password`, `passwd`, `pwd`, `secret`, `token` or `api key`
(`api[_-]?key`), in any case, has its whole value replaced, whatever its type: `[MASKED:api-key]` for an API key
name, `[MASKED:bearer-token]` for a token name, otherwise `[MASKED:password]` (P1-62). A count is
therefore never written under such a name: the Ollama context size is logged as `contextSize`, not `contextTokens`
(P1-112). Records kept by the shared deep masking (provider call lines, transcripts, run events, audit details) apply the
same whole-value rule to a key whose last word is `secret`, `secrets`, `token`, `authorization` or `bearer`
(`accessToken`, `client_secret`, `X-Auth-Token`, `proxyAuthorization`), or whose last two words are `secret key`,
`secret value` or `token value` (`secretKey`, `tokenValue`, `accessTokenValue`), or the plural `tokens` after a word
that names a credential (`access`, `refresh`, `id`, `auth`, `bearer`, `session`, `api`, `jwt`: `refreshTokens`,
`access_tokens`), besides the `password`, `passwd` and `pwd` keys they already had. Keys are split into words at
camelCase, acronym runs, `_`, `-` and digits, and a short suffix that starts with a digit (`2`, `_2FA`) is not a word,
so `Secret2FA` and `Secret_2FA` match; the last words decide, so `inputTokens`, `timeToFirstTokenMs`, `secretCount`
and `primaryKey` keep their values (P1-112, P1-124).
When masking fails the entry is withheld (fail closed, DEC-57): a `warn` entry with logger `security`, code
`RST-2101` and the fixed message `Log entry withheld because secret masking failed.` is written instead, with
nothing of the original entry; it is filtered by its own level, so it reaches standard output at `info`.
The Logs panel (RF-1011, `GET /api/runs/:runId/logs`) reads these files through `FileApplicationLogReader` (at most 31 days, masked again on read) and shows an entry to the owner of a run only when its `runId` is the run's id and any `userId` it carries is the owner's, or its `runId` is the run's key and its `userId` is the owner's. An entry with the key and no user is never shown: the key is unique per project only and a deleted run's entries stay in the files, so it may belong to another user's run that is gone (P1-122). The run's own writers therefore name the owner beside the key: `ownerLogger` for the understand session and for the egress and budget guards that the provider factory builds for the run (their security events and cap refusals), and the queue and the lifecycle directly.

### 3.15 `transcripts/<agentTaskId>.jsonl`

The judgement step (RF-301) uses one agent task id per claim, `verifier-<claimId>` (for example
`verifier-BR-001.c1`), so the claim's call and its one retry form one conversation and one transcript.

The masked messages exchanged with the model for one agent task, one message per line `{ schemaVersion, seq, at,
callId, role (system, user, assistant, tool), content, toolCalls? }`. Written unless the project setting `output.transcripts` is false (DEC-43).
Content is exactly what was sent after masking, so it may contain excerpts of the legacy code. Writer: the
`ObservedProvider` through `ProviderCallRecorder` (RF-408): the system prompt on the task's first call, then each
call's new messages before it is sent and its answer after. The messages of a task are append-only (each call repeats
the earlier ones unchanged), so only the new ones are written. Every key and string is masked, and every value is
masked again together with its property name, so a secret held under a key such as `password` is masked too, and so
is each item of an array held under such a key; when masking fails nothing is written and the call is not sent
(DEC-57). The agent task id must be a plain file name. `seq` continues after the lines a file already holds, so a
resumed run (RF-006) never repeats a number; a partial last line left by a crash mid-append is counted and kept as
it is, and the next record starts on a new line.
The same holds for `provider-calls.jsonl`.

### 3.16 `answers.md`

Generated skeleton, then edited by the user on the answers page (RF-240, RF-1007, Q-11). One section per open question:

```markdown
## OQ-003 - Is a catalog item with zero stock still shown?

- Card: runs/20261010-140322-understand/cards/OQ/OQ-003.md
- Context: Catalog/Default.aspx.cs:41-58 filters on ...
- Answer:
```

The heading carries the card id and the run, so a later run matches answers by card id and question text; an
existing answer is never overwritten. `RunUnderstand` adds the `OQ` cards of the run when it ends (stopped runs
included): a question whose heading text is already in the file is skipped, new sections are appended after the
existing ones, the question and context are one line each and masked, and the context is the card's first citation
followed by its first claim (P1-33, DEC-98). The same question asked by several areas or twice in one (Q-52; equal ignoring case and punctuation) is added once, under the first card's id and wording, and its context ends with `(also cited: ...)` listing the citations of the other cards (RF-243); the new sections are ordered by area, the area whose questions have most dependants first, and inside an area the question with most dependants first, where a question's dependants are the cards that are not open questions and cite a file one of its cards cites. A question asking what the code, an area or the application does never reaches a card (it is refused at parsing, RF-243), and an area of third-party code writes none.

A run started with the answers option (RF-241, P2-05) reads the sections whose answer line has text and whose `- Card:` line is exactly `runs/<run folder>/cards/OQ/<card id>.md` for that section's own heading; any other card line (another card, a path out of a run folder) names no run and the section is ignored.

The live run page records answers (`RecordAnswers`, P1-39, RF-1007): a question belongs to the run its `- Card:` line
names, and an answer replaces the text after `- Answer:` on that section's first answer line (a section that lost the
line gets it after its last line). The answer is masked and written on one line (line breaks become spaces, so it can
never start a heading or another field); an empty answer leaves `- Answer:` bare. No other line of the file changes,
and writes to one project's file run one after another. A file saved with CRLF or lone CR (old Mac) line ends, or with a
byte-order mark before its first line, is read like one with LF. Every line keeps its own line end, also in a file that
mixes them; a new answer line or appended section takes the end of the line before it, and the mark is kept, also in a
file that holds only the mark (P1-126, P1-135).

`data-model.md` is written from a third planner call, after the plan and the PRD (`planner/data-model.v1.md`, task id `planner-data-model`, recorded in `promptVersions`), made only when the supported cards hold an `ENT` claim; otherwise the file says there is no legacy entity. The legacy data model has claims, not structured fields, so a legacy field is a supported `ENT` claim: every such claim is mapped by a column or listed as dropped, and a claim the planner did neither for is listed as dropped by the code ("not named"). A column naming an unsupported claim is written as new; a table or column whose name is not an identifier, a type that is not a type name (written "to confirm") and a key, index or foreign key over missing columns or tables are left out and logged. Foreign keys draw the ER relations with the cardinality the key states. An answer with no usable table does not fail the run, like an unreadable PRD: the run completes, `data-model.md` lists every legacy claim as dropped ("not named") and a warning is logged.

`flows/` is written from a fourth planner call, after the data model (`planner/flows.v1.md`, task id `planner-flows`, recorded in `promptVersions`), made only when the supported cards hold a `FLOW` card and the plan names a component; otherwise the index says no journey is mapped (or lists every journey as out of scope because the architecture has no component). Every verified `FLOW` card (one with a supported step) is mapped or listed as out of scope: a card the planner left unmentioned, whose steps it placed in no component or that is over the cap of 15 is listed by the code with a reason that says so. A step is a supported claim of its own card; a step naming a card or component that does not exist is refused and logged. An answer that cannot be read does not fail the run: the run completes with every journey out of scope and a warning.

`api/openapi.yaml` is written from a fifth planner call, after the flows (`planner/api-contract.v1.md`, task id `planner-api-contract`, recorded in `promptVersions`), made only when the brief names a front end and the supported cards hold a `FEAT` or `FLOW` card; otherwise the README says no contract applies and why (no front end named, or no verified feature or flow) and no file is written. The planner decides from the brief whether the front end is separate; an answer that says it is not gives the reason the README shows. The planner's operations are checked: an operation id is an identifier, a path is `/` or plain lower-case segments and `{parameters}`, a method one of get, post, put, patch and delete, a summary is not empty, every operation serves at least one verified `FEAT` or `FLOW` card, and a repeated operation id or route is left out; the error statuses the planner may add are 400, 403, 404, 409, 422 and 429 (401 and 500 are added by the code); an operation that carries a table is never public. The body of an operation is the table built from the `ENT` card it names. Every `FEAT` or `FLOW` card no operation serves is listed in the README with a reason. The YAML text comes from the serializer, never from joined strings. An unreadable answer, or one with no usable operation, writes no file and says so in the README.

`ux/` is written from a sixth planner call, after the API contract (`planner/ux.v1.md`, task id `planner-ux`, recorded in `promptVersions`), made only when the supported cards hold a `SCRN` card; otherwise `ux/README.md` says no verified screen card exists and nothing else is written under `ux/`. `ux/README.md` holds the target screen map (a Mermaid flowchart generated by code), a table of every verified `SCRN` card with its decision (`kept` alone in a screen, `merged` with others, `dropped`), its target screen and the reason, and the list of wireframes. `ux/wireframes/<SCRN id>.html` is one plain HTML file per main screen, at most 20 (Q-27), named by the first legacy card of the screen: layout boxes only (a border and spacing), no script, no event attribute, no external resource, a policy that refuses everything but inline style, every text value masked and escaped; its fields, actions, roles and navigation come from the legacy cards the screen replaces, never from the planner (an action, field, role or link only when the claim that states it is `Supported`; a field of an old card that no claim states is drawn marked "not checked" and never sent to the planner; a screen whose fields are all unsupported says "fields not confirmed"), and a link goes only to the wireframe of another target screen. `ux/design-brief.md` is the brief for an external design tool: audience, tone, front end, components needed, the screens to design and the accessibility target WCAG 2.1 AA; a part the planner left empty is a marked placeholder. An answer that cannot be read does not fail the run: every screen is dropped and a warning is logged. The package holds no generated visual design (RF-626).

`checks.md` and the `Builds:` lines of `tasks.md` come from a seventh planner call, after the documents (`planner/coverage.v1.md`, task id `planner-coverage`, recorded in `promptVersions`), made when the plan has a task card and the package an item. An item is a feature (`feature:F-001`, numbered in the order of the PRD), a table (`table:<name>`), an operation (`operation:<operationId>`), a mapped journey (`flow:<FLOW-id>`) or a target screen (`screen:<SCRN-id>`); a task card covers an item only by listing its id, so a title that names an item builds nothing, and a repeated link or one to an id that is no item is dropped. When items are still uncovered, one more planner call (`planner/gap.v1.md`, task id `planner-gap`, recorded in `promptVersions`, Q-45) lists only those items and asks for task cards that build them; the cards that pass the card rules join the plan after the last (`T-` ids continue the numbering) and the items they build are linked in `Builds:`. A gap card the plan does not take is left out the same way (a phase outside the plan, a risk class that does not exist, an invariant missing, a Done-when item that is not Given, When, Then, a guard with no probes, no requirement under SDD, or builds that name no item still uncovered). Once the cards are linked, a card that builds an item lists the requirements that cite a source card of that item and no requirement that cites none of the source cards of what it builds but cites one behind an item another card builds (the planner counts its requirements by position and sometimes miscounts); a requirement that no other card builds an item behind, because it cites only cards no item is built on (a rule, a question) or an item nobody builds, has no other card and stays (DEC-160); a card that builds nothing, an item with no source card, and the last requirement of a card change nothing (RF-627, P3-95). `checks.md` then lists, under "Requirements of the task cards", each requirement added to or taken off a card, each requirement kept because none of the card's requirements fit what it builds (the line says whether it is the only one), and each requirement position of a task card in the plan answer that the list of requirements does not have (it is ignored).

Ids are numbered in the order the planner wrote the items, after the checks. The file set is written file by file
(each file whole or absent); a write that fails ends the run `Failed` with RST-1804.

### 3.18 Price table

Shipped as `prices/default-prices.yaml` in the Rosetta repository: `{ schemaVersion, version (date),
currency, models: [{ provider kind, model, inputPerMillionMicros, outputPerMillionMicros,
cachedInputPerMillionMicros, cacheWriteInputPerMillionMicros?, longPrompt? }] }`. Ollama models have price 0. Overrides in the
configuration use the same entry shape (RF-420, RF-427). `cacheWriteInputPerMillionMicros` (P2-16, an additive
optional field, so the schema version stays 1) prices the tokens a call writes to the provider's prompt cache:
Anthropic bills them at 1.25 times the input price, so an entry of provider kind `anthropic` without it prices
nothing and the call is handled as for a model missing from the table (unpriced, RF-427), and a project override
without it leaves the shipped entry to price the call. Other kinds bill no cache write of their own: an entry without
the field prices any written token as input (the shipped OpenAI entries repeat the input price), and a local model
missing from the table writes for free. The worst case of a call prices its whole prompt at the highest of the
input, cached input and cache-write prices (RF-422). Every price is a whole number of micro-dollars up to 2^53 - 1 and a model is listed once per
provider kind; a file that breaks this stops the server with `RST-1602`. A call priced with a project override
(user's own key only, DEC-107) records the version `<version>+project`.

`longPrompt` (Q-56, an additive optional field, so the schema version stays 1) is the one tier a model may carry for a price by prompt length: `{ overInputTokens, inputPerMillionMicros,
outputPerMillionMicros, cachedInputPerMillionMicros, cacheWriteInputPerMillionMicros }`, every field required (a tier missing a price,
a threshold that is not a positive whole number or a second tier stops the server with `RST-1602`). A call whose input tokens, cache reads and
writes included, are over `overInputTokens` is priced at the tier's prices in the ledger, the meter and the call log; a call of exactly the
threshold or less is priced at the entry's own. The cap check prices a call at the tier its measured prompt reaches, and the estimate at the
tier the estimated prompt of one call reaches (the average prompt for the low and likely figures, the largest for the high figure). Claude
Haiku 5.5 carries a tier over 100,000 tokens and the OpenAI flagships one over 272,000. A project override has no tier: it replaces the
shipped entry, tier included, on the user's own key.

The model list `prices/models.yaml` (DEC-156, RF-405) sits beside it: `{ schemaVersion: 1, version (date), models: [{ provider (anthropic or openai), model, label, contextTokens?, maxOutputTokens?, reasoning? }] }`, a model once per provider, read at start-up with the price table; a file that breaks this stops the server with `RST-1602`. `contextTokens` and `maxOutputTokens` are the context window and the maximum output of the provider's model page, positive whole numbers, left out when no page confirms them; a hosted role runs with them (Q-57, providers.md section 3.6). `reasoning: true` (Q-58) marks a model that takes a reasoning effort on its provider's API. It feeds the model dropdowns and the limits of the roles and prices nothing: a listed model the price table has no entry for shows as "no price" (RF-427). Ollama is not listed, because its models are the ones installed on the configured server.

### 3.19 Evaluation results: `eval-out/<id>/`

Written by `npm run eval` (RNF-006, RNF-012, RNF-015, RF-305), inside the Rosetta repository's git-ignored `eval-out/`, never
in a user's project: `experiment.json` `{ schemaVersion, id, at, rosettaVersion, roles (with modelVersion and
modelDigest), promptVersions (with sha256), goldenSetVersion, repetitions }` and `results.json` with per-case scores
per repetition, precision, recall, the spread across repetitions, cost per supported claim, and, with the calibration
set, the verifier's agreement rate.

As built by P2-11 (schemas in `src/application/eval/evaluation-schema.ts`; the runner writes only what parses, masked,
into a folder that must not exist yet, tried once more under a new id when it cannot be written, and printed by the
command with `RST-1701` when that fails too; the folder name and `id` are `yyyyMMdd-HHmmss-eval`, the date and the id
in one):

- `experiment.json`: `schemaVersion` 1, `id`, `at` (ISO instant), `rosettaVersion`, `goldenSetVersion`,
  `goldenSetSha256` (of the golden set file's bytes), `repetitions` (at least 3), `source { url, commit, subpath }`,
  `areas` (the code-map areas that hold a golden path, the only areas run), `roles` (per role `{ provider, kind, model,
modelVersion, modelDigest, toolMode, maxOutputTokens, temperature, maxTurns }`, taken from the runs' manifests),
  `promptVersions` (prompt file name to `{ version, sha256 }`: the manifests' prompts plus the verifier's) and
  `settings` (`parallelism`, `runCapMicros`, `runMaxTokens`, `areaTokenBudget`, `maxFileBytes`,
  `priceTableVersion`, `totalCapMicros`).
- `results.json`: `schemaVersion` 1, `experimentId`, `goldenSetVersion`; `repetitions[]` with `repetition`, `runId`,
  `endState`, `errorCode`, `modelVersions` (role to version), `costMicros` (`totals.costMicros` of the run's
  `cost.json`), `supportedClaims`, `costPerSupportedClaimMicros`, `overall` and `cases[]` scores, `citationValidity
{ checked, valid, rate, invalid[] }` and `estimate` (`measured` with `likelyMicros`, `actualMicros`, signed
  `error` and `withinTarget` (within 30%, compared before the error is rounded), or `not-measured` with the reason
  `unpriced`, `free` (estimate and cost both zero), `zero-estimate` (a priced estimate of zero for a run that cost
  money) or `no-cost-report`); `summary` with the spread `{ n, min, max, mean, stdDev }` of precision, strict
  precision, rule recall, recall of all findings, step recall, screen field recall, relation precision, citation
  validity, cost, cost per Supported claim, estimate error and the unmatched share (unmatched / Supported);
  `cases[]` with the spread of each case's precision, recalls, step recall, screen field recall and relation precision; `targets` (precision 0.9, rule recall 0.7, citation
  validity 1, each `{ target, mean, met }`; precision also has `strictMean` and `unmatchedShare`, the means of strict
  precision and of the unmatched share, so a headline met with most claims unchecked shows it; and the estimate
  `{ target: 0.3, measured, within }`).
- A score counts only `Supported` claims: `correct` (matches a finding), `incorrect` (states an absence; an absence
  wins over a finding), `unmatched` (neither, listed by claim id for a person to check), `precision` = correct /
  (correct + incorrect), `strictPrecision` = correct / Supported, `recall` = golden rules found / golden rules,
  `recallAll` over the features, rules and entities. The flows, screens and data model (RF-260..RF-262, P2-23) have
  three measures of their own, with counts and no target: `stepRecall` = golden steps found / golden steps (a step is
  found by a correct `FLOW` claim), `screenFieldRecall` = golden screen fields found / golden fields (by a correct
  `SCRN` claim; the golden actions are found or missed but not in this ratio), and `relationPrecision` =
  `relationsCorrect` / `relationsStated`, where a relation is stated by a `Supported` `ENT` claim that holds a relation
  word (`refer*`, `foreign key*`, `belong*`, `relat*`, `link*`, `join*`, `associat*`, `has many`, `has one`,
  `one-to-many`, `many-to-one`, `one-to-one`, `many-to-many`; `ENT` cards hold claims, not structured relations) and is
  correct when it matches a golden relation; `relationClaims` lists the claims that stated one. A ratio with nothing to
  divide by is `null`; every measure is rounded to six
  decimals. A case is scored with the claims that cite one of its paths.

The calibration set of RF-305 is not part of P2-11; P2-03 adds it (below).

**Golden set** (`eval/golden/<name>.json`, schema in `src/application/eval/golden-set-schema.ts`, at most 1 MiB, read
only from inside `eval/`): `{ schemaVersion: 1, version, description, source { url (https://github.com/<owner>/<repo>),
commit (40 hex), subpath }, cases[] }`; each case `{ id, title, paths[], findings[], absences[] }`; a finding `{ id,
kind (feature | rule | entity | step | field | action | relation), of (the flow, screen or entity; required for
step, field, action and relation), statement, cardTypes[] (empty: any), evidence[] (path:start-end inside the case's
paths), keywords[] }` is matched by a claim of an accepted card type that cites a line of its evidence and names one
keyword (in the claim text or card title, any case); an absence `{ id, statement, claimPatterns[][], unless[] }` is
hit by a claim that holds every word of one pattern and none of the `unless` words. Words are whole words: a word
also matches its `-s`, `-es`, `-d`, `-ed` and `-ing` forms (`add` is in "adds" but not in "address", `10` is not in
"100"), and a stem ending in `*` matches any word that starts with it (`generat*`). A `*` anywhere else, and a pattern
word that holds one of its absence's `unless` words (it could never match), are refused. Ids are unique in the set
and the set must hold at least one absence (DEC-57). The provenance of each golden set is in `eval/README.md`. **Settings** (`eval/config.json`): `{ schemaVersion: 1, goldenSet,
repetitions (3..20), roles { reader?, verifier?, summariser? : { provider, model } }, runCapMicros, totalCapMicros,
parallelism? }`.

**Calibration** (RF-305, DEC-57, P2-03): `npm run eval -- --calibration` judges the claims of a calibration set with the
`verifier` role of each model and writes `eval-out/<id>/calibration.json` (`<id>` is `yyyyMMdd-HHmmss-calibration`; the
folder must not exist yet, tried once more under a new id when it cannot be written, printed with RST-1701 when that
fails too). The set is `eval/calibration/<name>.json`, schema in `src/application/eval/calibration-set-schema.ts`, at
most 1 MiB, read only from inside `eval/`: `{ schemaVersion: 1, version, description, source { folder }, claims[] }`;
`source.folder` is a relative folder of the Rosetta repository (a repository fixture, read-only through the same reader
the agents use) and each claim is `{ id, text, citations[] (path:start-end inside the folder), supported (the hand label:
whether the cited lines, with the verifier's margin of three lines, show what the claim says), note (why) }`. Ids are unique
and the set holds at least one supported and one not supported claim. Every cited range is read before the first model
call, so a set that cites lines the folder does not hold stops with RST-1000 at no cost. Each claim is judged exactly as the
judgement step of a run judges it (RF-301: the claim and only the cited lines as data blocks, the reason before the verdict,
one retry, the guarded provider factory), one model after the other, one claim after the other.
`calibration.json`: `schemaVersion` 1, `id`, `at`, `rosettaVersion`, `calibrationSetVersion`, `calibrationSetSha256`, `claims`,
`promptVersions` (the verifier's prompt files to `{ version, sha256 }`) and `models[]` in the order asked, each `{ provider,
model, modelVersion, endState (Completed, CapReached or Stopped), claims, agreed, agreementRate, falseSupported, falseRejected,
unjudged, disagreements[] { claimId, label, verdict, reason } }`. A verdict agrees when it equals the label (`Supported` for a
supported claim, `Rejected` for the others); a claim left `Unverified` (an answer that could not be read after the retry, a
failed call, the cap or a stop) never agrees and is counted in `unjudged`, so a model that could not finish does not score
better than its answers. `falseSupported` counts claims called `Supported` against the label (the error that lets a false
statement through) and `falseRejected` the supported claims it rejected. `agreementRate` is `agreed / claims` to six
decimals. The settings file's optional `calibration` section is `{ set, models[] { provider, model }, capMicros }`: the models
are those whose agreement is reported, and `capMicros` bounds the whole calibration (the calibration account's daily cap, so
the budget guard stops the call that would pass it); `--verifier provider:model` replaces the models. As for the golden runs,
nothing is sent without `--yes` (RF-143). The tests drive the same code with the fake provider and recorded answers.

### 3.20 `planning-brief.json` (added 2026-10-11)

The answers saved by Plan setup (RF-605, ADR-018): `{ schemaVersion, savedAt, catalogueVersion,
principles: [entryId], architecture: { style, recommended: [style], evidence: [cardId] },
migration: "strangler-fig" | "parallel-change" | "rewrite", stack: [{ layer, choice, custom }],
context: { teamSize, experience, deadline, keepIntegrations: [text], dataMigration }, buildMethod: { aiAssisted },
defaulted: [questionId] }`. `defaulted` lists the questions that took their default, so the package can list them
as open questions (RF-604). Free-text answers are untrusted input: they reach the planner only inside labelled data
blocks (ADR-013). `plan` copies the brief and the catalogue version into the run manifest (RNF-004).

Rules (P3-06): a question the user did not answer takes its default and is named in `defaulted`, as `principles`,
`architecture`, `migration`, `stack.<layer>` (one per layer of RF-609: `language-runtime`, `backend-framework`,
`front-end`, `database`, `data-access`, `testing`, `hosting`), `context.<field>` and `buildMethod`. The defaults are:
the catalogue entries switched on (DEC-74) for `principles`, `strangler-fig` for `migration` (RF-610),
`layered` for `architecture.style` with no recommendation, `{ aiAssisted: false }`, no `stack` entry for an
unanswered layer, and `null` or an empty list for the context fields; nothing is invented (DEC-80). `principles`
holds catalogue entry ids other than the architecture styles, sorted and without repeats; `stack` holds at most one
entry per layer, in layer order, each choice at most 200 characters; the context texts at most 500 characters, up to
20 integrations, `teamSize` a whole number from 1 to 10000. The file is replaced whole by each save and not touched
when the answers are the same as the stored ones, so `savedAt` moves only with a change. The brief is _out of date_
when `savedAt` is later than the start of the newest `Completed` run of stage `plan` of the project (the package
was written from an earlier brief); a project with no such run is never out of date.

## 6. Access

**Database roles** (ADR-016):

| Role               | Rights                                                                                                                                                                                                                                                                                                                           | Used by                                                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `rosetta_migrator` | owns the schema; `CREATE`, `ALTER`, `DROP`                                                                                                                                                                                                                                                                                       | the one-off migrate step only (`DATABASE_MIGRATOR_URL`; the one role's URL when the host offers one role); never the server, which refuses that variable (DEC-140) |
| `rosetta_app`      | `SELECT`, `INSERT`, `UPDATE`, `DELETE` on the tables (including `cost_reservations`); `INSERT`, `SELECT` only on `cost_ledger` and `audit_events` (no update or delete); `EXECUTE` on the function `purge_audit_events_before` and on no other function (DEC-132); `SELECT` only on `schema_version` (migration `0010`, DEC-140) | the server (`DATABASE_URL`)                                                                                                                                        |

The roles are created outside the migrations, because a committed file cannot hold their passwords: locally by a
Compose init script (`db/init/roles.sh`) that reads the passwords from `.env`, hosted by the runbook in the host's
console; migrations only `GRANT` and `ALTER DEFAULT PRIVILEGES` (DEC-112).

When the host provides a single database user, both roles collapse into it and the runbook records that; the server
then logs a warning at every start, because it runs as the owner of the audit and ledger tables (DEC-140). Each
migration therefore grants to `rosetta_app` only when that role exists. `schema_version` belongs to the migration
runner; `rosetta_app` may only read it, so the server can refuse a schema with a pending, changed or unknown migration
(RST-2405, RST-2401, RST-2402) instead of migrating it.

**Files**:

- Rosetta writes only inside `<data>` (RF-005); workspace paths are built from ids, then resolved and checked to be
  inside `<data>/users/<actor userId>/`.
- Snapshots are read-only after the fetch (3.3) and are never listed to users.
- The web server serves workspace files only through routes that check the owner (RF-1105), and its own static
  assets; it never serves `<data>` directly.

## 7. Migrations and schema versions

**Database migrations** (RF-1302): files `db/migrations/NNNN_snake_name.sql`, four digits, applied in order, each in
a transaction, recorded in `schema_version` with its checksum, by the one-off migrate step
(`node dist/presentation/migrate.js`, DEC-140) before the server starts; the server only checks them. An applied file is never edited; a fix is a new
migration. Number blocks: `0001..0099` release 1 (`0001_accounts`, `0002_projects_runs`, `0003_cost_ledger_audit`
with `cost_reservations`, `0004_server_settings_defaults`, `0005_cost_ledger_tasks_and_tokens`, `0006_cost_reservations_without_run`, `0007_cost_reservations_per_run_call`, `0008_audit_retention_purge`, `0009_project_settings_version`, `0010_schema_version_read`, `0011_runs_failed_areas`, `0012_cost_reservations_role`, `0013_cost_ledger_cache_writes`, `0014_project_source_kind`, `0015_project_upload_source`, `0016_project_workbook_source`, `0017_project_workbook_source_columns`), `0100..` later
releases.

**File schema versions**:

- Each file kind has its own `schemaVersion`, starting at 1.
- An additive change (a new optional field, a new event type) keeps the version. A change that renames, removes or
  changes the meaning of a field raises it.
- Readers accept the current and the previous version and upgrade the previous one in memory; old run folders are
  never rewritten (DEC-43).
- The version table below is updated in the same pull request as the change.

| File kind                                                                                                                                                  | Current version |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------- |
| project settings, snapshot, code map, manifest, card, card index, coverage, events, provider calls, egress, cost, application log, transcript, price table | 1               |

## 8. Test data strategy

- Unit tests use in-memory adapters (`MemorySink`, `MemoryLogger`, memory file system); no disk.
- Integration tests create a temporary project folder per test and delete it afterwards; snapshots come from small
  fixture archives under `tests/fixtures/snapshots/`, including one with a path-traversal entry (RF-122).
- Provider traffic comes from recorded responses under `tests/recordings/` through the fake provider (ADR-008);
  GitHub traffic from a fake GitHub client.
- Fixture code from the demo app is limited to small cited excerpts (MIT, attribution kept).
- Database integration tests use the PostgreSQL at `ROSETTA_TEST_DATABASE_URL` (the CI service container, or the
  Compose `db` service locally), apply every migration, and give each test file its own schema; unit tests use the
  memory repositories (DEC-112).
- Test accounts and passwords are generated by the test helpers; none is a real credential.
