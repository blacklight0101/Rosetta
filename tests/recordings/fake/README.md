# Fake provider recordings

Scripts for the fake provider (`src/infrastructure/providers/fake/`), which replays them instead of calling a model
(ADR-008). Each file lists calls in order, with the attempts of each call and the answer or failure of each attempt:
the reader tasks of the `webforms-csharp` fixture, an injection attempt, a bad tool call, a turn limit, a cost cap,
a stop, the full understand run that the end-to-end tests drive, and the verifier's judgement of its claims
(`verifier-*.json`: the verdicts, a retry, a verdict written before its reason, an answer invalid twice and a Supported answer to every claim; `verifier-flow-screen.json` judges a FLOW and a SCRN card with a bad step and made-up claims, `verifier-flow-step-rejected.json` rejects one step of the `webforms-shop` run, P2-20).
`understand-flows-screens.json` is a run over the `webforms-shop` fixture whose readers answer FLOW, SCRN and OQ cards
for the catalogue and order journeys and none for the service library (P2-19).
`understand-shop-model.json` is the same run with the Services area answering two `ENT` cards (one relation the code shows, one it does not) and the shipping `BR` card, and `verifier-shop-model.json` judges it (the second and fourth claims rejected, the rest Supported); the evaluation runner test scores them against `tests/fixtures/eval/golden-shop.json` (P2-23).
`plan-options.json` is the `planner` role answering the Plan setup options (RF-608, RF-609, P3-07): two architecture styles with trade-offs and evidence, one recommended, and two options for each of the seven stack layers, each a name and a description (the shape of planner/options.v2.md, P7-10).
`planner-package.json` holds the planner's two answers for the hand-off package of a seeded order-shop run. The first is the plan: requirements that cite supported cards, one that cites only a card without a supported claim, one holding hostile Markdown and HTML, an entity mapping without a supported card and a task in a phase that does not exist (P3-09). The second is the product requirements document: features that cite `FEAT` cards (one only a card without a supported claim, one holding hostile Markdown and HTML), rules that cite `BR` cards (one citing a `FEAT` card), an out-of-scope item and no roles (P3-15). A third call is the data model (RF-623, P3-17): tables over supported ENT claims, a column whose claim is not supported, a type that is not a type name, a name that is not an identifier, a foreign key to a missing table and a dropped field. A fourth call is the target flows (RF-625, P3-19): FLOW-001 mapped, with a step in a component the architecture lacks, a rejected step, a step of another card and a repeated step; FLOW-002 out of scope with a reason; FLOW-077, which no card has; FLOW-003 left unmentioned. Runs whose cards hold no `FLOW` card never make that call. A sixth call is the user-interface material (RF-626, P3-20): Orders merging SCRN-001 and SCRN-002 (its purpose holding hostile HTML), Checkout keeping SCRN-003 (its name holding a script) with a card nobody has, a screen of a card nobody has, a screen of a card already placed, SCRN-004 dropped with a reason, a drop of a card already kept and of a card nobody has, SCRN-005 left unmentioned, and a design brief holding hostile HTML. Runs whose cards hold no `SCRN` card never make that call.
`planner-webforms-proposed.json` is `planner-package.json` with the file paths of the two task cards written for the stack Rosetta proposes for a WebForms site (Razor Pages and C# files), for the plan run whose brief names no stack (P5-39, RF-609).

`planner-coverage.json` is the planner's answer to the coverage call (RF-627, P3-21), kept apart because the call comes last whichever documents were asked for: it links the two task cards to the items they build, and names an item that does not exist, a text that is no id and a repeated link, all of which build nothing.
`planner-gap.json` is the planner's answer to the call for the items no task card builds (Q-45, P3-72), for a run whose coverage answer linked only the first feature: three task cards that build the nine items left over, one of them naming a table and a feature a card already builds and an id that does not exist (all of which build nothing), and a fourth card in a phase that does not exist (left out).
`planner-gap-positions.json` is the same call answered the way a small model (Ollama `gemma4:e4b`) did in an evaluation (Q-54, P3-82): five task cards that build the nine items left over, each writing `requirements` and `dependsOn` as objects (`{"position": 3}`, `{"position": 4, "builds": ["T-004"]}`) instead of numbers. The cards are synthetic; no employer text.
`planner-gap-item-depends.json` is the same call and its repair, shaped like the answers of a small model in the evaluation of 2026-10-29 (P7-14, plan `a9700a80`): the gap answer names item ids such as `operation:placeOrder` in `dependsOn` and puts one card in a phase that does not exist; the repair answer is not JSON as a whole (one card writes `"requirements": [ none ]`) and writes a `dependsOn` position as a digit string. `planner-gap-empty-requirements.json` is the same call under SDD shaped like plan `8ff8e480` (P7-14): two cards with `"requirements": []`, one building operations a requirement covers and one building a journey and screens no requirement cites. Both are synthetic; no employer text.
`planner-trd.json` is the same answer with a technical part for `trd.md`: integrations (one for an unknown card, one repeated), four security controls (two denylists, one with no supported card), two non-functional targets (one with no source card) and two environments (one naming a decision that does not exist) (P3-16).

`understand-shop-journey.json`, `verifier-shop-journey.json`, `planner-shop.json` and `planner-shop-coverage.json` are the recordings of the documentation-set journey (P3-22, `tests/integration/journeys/`): the `webforms-shop` demo understood in four areas (the flows, screens, entities and rule of `understand-shop-model.json` plus three `FEAT` cards, and the summariser's overview as the ninth call); the verifier judging it (it rejects the second step of the first flow, the free statement of the first screen and the field `PromoCode` of the checkout screen; the derived field claims are decided by the cited lines without a model, so the recording holds no call for them, P3-122); the planner's six answers (plan, PRD, data model, flows, API contract, user-interface material) over the cards that run writes; and the planner's coverage links. The journey replays the reader's nine calls and then the planner's six from one fake, in that order.

`understand-workbook.json` is an understand run over the `pricing-workbook` fixture (a rendered Excel workbook beside a C# helper, as an uploaded zip holding a workbook): the workbook area reads the Quote sheet's formulas and values (a cell there holds a planted instruction) and writes two `BR` cards and an `ENT` card, the helper area writes one `BR` card; `verifier-all-supported.json` judges it. `planner-workbook.json` holds the planner's plan and product requirements document for a seeded run over that workbook (a quote form, a pricing service and rate data replacing it). Both are P3-50 (RF-155).

`understand-retry-run-again.json` and `understand-retry-run-recovers.json` are the reader calls of a run over Catalog and Services in which Catalog gives no card and Services gives one, followed by the runs that retry Catalog alone (RF-208, Q-43, P3-69): in the first file two retries end without a card again, in the second the retry gives its card.

`verifier-heavy-supported.json` is `verifier-all-supported.json` with 6,000 input tokens reported for each verdict, so a run cap can be set at which the verdicts would use everything the readers left; the share of the run token cap the verifier may use keeps the rest for the summariser (RF-429, P3-121).

`deepen-claim-heavy.json` and `verifier-deepen-claim-heavy.json` are `deepen-coverage.json` and `verifier-deepen-supported.json` with the Deepen's re-read task writing twelve claims, so that at a run cap of 100,000 tokens the readers stop before the second task and every claim is judged (RF-429, P5-30).

`deepen-database-objects.json` and `verifier-deepen-database-objects.json` are a run on a Clinic area (a synthetic SQL script, `tests/fixtures/sql/clinic.sql`, copied into the `webforms-csharp` fixture) whose reader states only the table, then a Deepen whose one task reads the four objects with no card and states each; every claim is Supported (P5-36).

`planner-single-file.json` holds the planner's plan (three task cards across the difficulty bands, one at risk of money) and product requirements document for a seeded run over a single-file application, a bill splitter that is one script. The method end-to-end test plans it with agents building, for Claude Code and for Codex, and reads the package (P6-12, RF-612, RF-639..RF-643).

## Provenance (RNF-009)

Every file was written by hand for this repository by the Rosetta contributors and is covered by the repository's MIT
licence. No real provider was called. The text of the answers describes the synthetic repositories of
`tests/fixtures/repos/`, which were also written for this repository. Each file says so in its `description` field.

Nothing here comes from the owner's employer (DEC-03).
